# D-08（#24 `8f3b2c1d4e5a`）修复方案 F1 / F3 完整定义

- 日期：2026-11-27
- 状态：**未实施**，等待 Owner 按六条标准裁决
- 前提事实（已取证）：降级 `DROP ROLE` 失败；本库残留 3 条（`public` schema ACL + `asset_service` 上 `project_planning_role` 的 TABLES/SEQUENCES 默认权限）；同集群其他 6 个库另有 170 条 `pg_shdepend` 依赖。
- 约束：角色是**集群级**对象；`DROP ROLE` 成功条件是该角色在所有数据库中都零依赖。

## F1：撤权 + 集群级零依赖断言（失败即阻断）

**做法**

1. 在 `8f3b2c1d4e5a.downgrade()` 内补齐 A 层撤权：
   - `project_planning_role` 在 `asset_service` 上的 TABLES/SEQUENCES 默认权限；
   - `asset_service_role` 在 `project_planning` 上的对称默认权限（若存在）；
   - `REVOKE USAGE ON SCHEMA public FROM project_planning_role, asset_service_role`；
   - 其余对象级授权按"角色 × 对象"逐条撤，不再按"角色↔自家 schema"配对。
2. 新增只读检查（同一迁移内，`op.execute` 一段 DO 块或 helper SQL）：
   `pg_shdepend` 中 `refobjid = <role oid>` 且 `deptype` 属于 ACL/OWNER 的行走 `dbid` 聚合；
   若存在**其他库**（`dbid <> current_database()`）的行 → `RAISE EXCEPTION`，
   消息中列出库名与依赖条数，并指向受控清理入口。
3. 断言通过才执行 `DROP ROLE`；失败时整个 downgrade 事务回滚，角色保留、结构回退成功。

**影响范围**

| 维度 | 影响 |
|---|---|
| 集群角色生命周期 | 仍会删除角色，但只在"集群内零依赖"时；不再静默 `IF EXISTS` |
| 其他库 ACL/属主/成员关系 | 不修改；只读取 `pg_shdepend` 并阻断 |
| 其他 revision / 业务域角色 | 只针对 #24 自己创建的两个角色；不触碰 `qc_worker` 等 |
| 既有部署 | 多库集群上**必然失败**（这是设计意图：把隐性问题变成显式错误） |
| 回滚 | downgrade 失败即回滚，无半完成状态；清理依赖后可重跑同一 downgrade |
| `role_specs.py` 一致性 | 只处理已登记的历史角色，不新增事实源；但"角色可被迁移删除"仍与 WP-02 判据相冲突 |

**代价**：迁移从"自包含"退化为"依赖外部清理脚本/人工操作"；CI 单库可通过，共享集群必失败。

## F3：不删角色，只撤权（推荐方向）

**做法**

1. 删除 `8f3b2c1d4e5a.downgrade()` 中的 `DROP ROLE`（保留全部 `REVOKE`，含 A 层补齐项）；
2. 角色留在集群中，属性维持 `NOLOGIN`（或按 `role_specs` 的退役属性收敛），并登记到
   `RETIRED_ROLES`（字段：`name / retired_at / reason / restore_policy / evidence`）；
3. 降级后的目标态改为：**"角色存在但零授权"**，而不是"角色不存在"；
4. `9e3b4c5d6e7f`、`7a8b9c0d1e2f`、`c5d6e7f8a9b0` 三处角色删除点按同一口径统一（WP-02 已经裁决"迁移不拥有角色删除权"）；
5. 需要彻底清角色时走 bootstrap 退役流程（`restore_retired_role` 的受控恢复契约已在 WP-03 落地）。

**影响范围**

| 维度 | 影响 |
|---|---|
| 集群角色生命周期 | 不再由迁移删除；只由运维/治理流程删除 |
| 其他库 | 无影响（不删角色，不需要清理别人的依赖） |
| 其他 revision / 业务域 | 不会误删；但"角色不存在"的断言需要同步修改 |
| 既有部署 | 安全：可在任何共享集群执行 |
| 回滚 | 最简单：再 upgrade 幂等重新授权；角色始终存在 |
| `role_specs.py` 一致性 | 完全一致：单一身份事实源 + 退役登记 |

**代价**：改变 #23 的"角色不存在"目标态，需要 ADR 修订；集群里会长期保留 NOLOGIN 角色（身份面增大，但零权限）。

## 按六条标准的对照

| 标准 | F1 | F3 |
|---|---|---|
| 1. 改变集群角色生命周期 | 是（条件删除） | 是（不再删除） |
| 2. 影响其他库 ACL/属主/成员 | 否（只读检查） | 否 |
| 3. 误删其他 revision 依赖的角色 | 低（零依赖才删） | 无（不删） |
| 4. 既有部署可安全执行 | 否（多库集群必失败） | 是 |
| 5. 可验证失败回滚 | 是（事务回滚） | 是（无需回滚） |
| 6. 与 `role_specs.py` 一致 | 部分（仍保留迁移删除权） | 完全一致 |

## 建议

- 默认采用 **F3**：与 WP-02 已裁决的"迁移不拥有角色删除权"一致，且对所有部署形态安全；
- 若 Owner 仍希望 CI 上保持"角色消失"的目标态，则采用 **F1**，但必须同时接受"共享集群降级必然显式失败"这一行为，并配套受控清理脚本；
- 两者都不允许用 `DROP ROLE IF EXISTS` 静默跳过。

**在裁决前，#24 保持不修改、不放行。**

# WP-04 可逆性矩阵 V2：集合比对与分级闸门

日期：2026-11-27　范围：只读脚本 + 单测，不改迁移、不连库、不提交

## 1. 为什么必须从 V1 升级

V1 只比较动作计数：`GRANT 12 ↔ REVOKE 12` 判对称。计数相等恰恰是最容易骗人的形态——
两个集合可以完全不重叠。V2 把每条语句解析成可比较元组：

```
(动作, 对象范围, 对象名, 角色, 权限集, grant option)
```

再做双向集合匹配：

| 升级 | 降级必须出现 | 缺失时的判定 |
| --- | --- | --- |
| `GRANT` | 同对象/同角色/同权限集的 `REVOKE` | `missing revoke` |
| `REVOKE`（撤既有授权） | 同集合的 `GRANT` 恢复 | `RISK:missing restore` |
| — | 降级多出来的 `GRANT` | `RISK:extra grant`（扩权，比漏恢复更严重） |
| `CREATE ROLE` | `DROP ROLE` | 身份泄漏 |
| 升级退役角色 | 降级重建 | 已退役身份复活 |
| 降级删除非本 revision 创建的角色 | — | 越权删除 |

覆盖规则（否则假阳性会淹没结论）：

- 权限集必须相等；`ALL` 视为覆盖任意子集；
- `ALL TABLES/SEQUENCES IN SCHEMA s` 覆盖该 schema 下逐对象授权；
- `WITH GRANT OPTION` 必须单独配对，普通 `REVOKE` 抹不掉 grant option；
- 对象在降级里被删除（表/函数/schema）时，视为"权限随对象消失"，只记 note；
- 角色在降级里被删除时，对该角色的授权只记 note；
- `RETIRED_ROLES` 登记的角色重建，由受控恢复契约管理，不算不对称；
- policy 只记 note（降级常靠 `DROP TABLE` 连带删除，盘点拿不到 DDL 语句）。

## 3. 闸门行为

`scripts/reversibility_matrix.py --check`：

- 有**未分类**的不对称 revision → exit 1，列出 revision；
- 有 `restore_required`（实测未恢复）→ exit 1，列出必须修的 revision；
- 有 `unproven_blocking` → exit 1，列出等待证据的 revision；
- 全部落在白名单且理由+证据齐全 → exit 0。

当前读数是预期的 FAIL：10 条 `restore_required` + 1 条 `unproven_blocking`（#24）。
这不是回归，是"修复未获授权"的诚实状态。

## 4. 已知局限（必须写进结论，不能当通过证据）

1. DDL 索引只覆盖 `op.<ddl>("literal")` 与 `op.execute("... DDL ...")` 的字面量；
   变量拼接、`sa.text(...)` 组合语句不会被识别，相关对象可能被误报为"未撤权"。
2. 盘点 JSON 只有身份类语句，没有列级/函数体级权限；列级 `GRANT UPDATE (col)` 归并为 `UPDATE`。
3. `policy` 只记 note，不参与判定。
4. 矩阵只证明"语句集合是否闭合"，不证明"真库 ACL 等价"——后者只能靠隔离库往返实验（已完成 22 个）。

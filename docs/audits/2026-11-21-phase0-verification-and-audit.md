## 0. 结论摘要

**Phase 0 的冻结机制可核验，但不能宣布「无保留通过」。**

字节层面的冻结证据是真实的：基线正文 489607 字节 / SHA-256 `9a9940c5…` 与登记一致，十一类产物哈希一致，
23 条修订的名称全集精确等于「基线 ∪ 已批准修订」，冻结清单自指哈希一致。这些都有 E2/E3 直接证据。

本次专项取证抓到两条此前一直全绿的**派生漂移**，都已按根因根治并验收：

1. **阶段表 Phase 2 与基线 §31.2 语义相反**（A-006）。派生文件允许 Phase 2 产生 CreatorRelease
   并在组织内自动发布，基线明文「不产生 CreatorRelease」且发布动作属 Phase 3。`freeze_manifest`
   只锁哈希，「漂移后重签」照样全绿。
2. **非权威阶段表登记漏项且行号陈旧**（A-007）。只登记 23.1 一处，漏掉 30.5；23.1 的行号 2719
   早已陈旧（实际标题在 2781）。这是手写清单的典型腐烂方向——加表即漏检，漏检表现为绿灯。

仍有一条**未闭环的权威表述矛盾**（A-008）：基线文件头写「已通过，条件 C1—C4 已关闭，owner 签署」，
§31.11 却写「当前为条件通过」，且同一段还规定「冻结状态以文件头部与决议为准，任何章节不得另述」。
这不是代码缺陷，不能由 AI 改冻结正文来消除，须由项目所有者裁定后走正式基准修订。

因此：`[FREEZE-STATUS] = PARTIAL`，`[RELEASE-STATUS] = BLOCKED`。可宣布「契约层冻结字节证据已核验」，
不可宣布「Phase 0 无保留通过」。

## 2. 审计发现

### A-006 阶段表派生文件与基线权威表语义相反

`[A-NONCOMPLIANT][P1-HIGH][IR-1.3.2-1]`

1. **基准条款**：§31.2 唯一阶段总表、§31.11 Gate C；基线明确 Phase 2「不产生 CreatorRelease」，
   `CREATOR.PUBLICATION.CHECK` / `CREATOR.RELEASE.PUBLISH` 属 Phase 3。
2. **代码证据**：`contracts/phases/phase_map.yaml` Phase 2 的 `community` 写「Creator Release 仅限私有
   与组织内受众，且必须经组织内发布审批」，与基线相反；`other_domain` 多出「Creator 公开发布能力先限于
   获准试点与自动化发布资格检查」。
3. **根本原因**：冻结机制只锁字节哈希，没有任何判据读基线正文；派生文件漂移后 `--write` 重签即可全绿。
4. **影响范围**：任何按 `phase_map.yaml` 判断阶段范围的路由、排期或自动化开关，都可能在 Phase 2 提前启用
   基线禁止的 CreatorRelease 发布链路。
5. **整改方案**：在 `scripts/contract_check.py` 增加 `check_phase_map_against_baseline()`，只解析 §31.2
   这一张有明确标题边界的表并逐格比对；派生文件改回基线，冻结清单重签。
6. **验收标准**：Phase 2 两列与基线 normalize 后完全一致；篡改任一格契约闸门报红；`freeze_manifest --check` PASS。
7. **实际整改**：已修（5 项负向用例覆盖语义漂移、漏阶段、未登记非权威表、陈旧行号、幻影登记）。
8. **整改状态**：`[R-VERIFIED]`。
9. **证据**：`tests/unit/test_contract_check.py::test_phase_map_detects_authoritative_text_drift`；
   C3.1；`freeze_manifest --check`。
10. **残余**：解析器只覆盖 §31.2 单表，属 ADR-R15 §6 明示的窄口径例外，不推广到通用正文反向解析。

### A-007 非权威阶段表登记是手写清单，漏项且陈旧

`[A-RISK][P2-MEDIUM][IR-1.3.2-1]`

1. **基准条款**：§31.11 Gate C「阶段总表与各章节 Phase 映射自动检查通过」。
2. **代码证据**：`non_authoritative_phase_tables` 只登记 23.1（且 `line: 2719` 指向 20.4 章节内部），
   基线中 30.5「全量阶段路线摘要」同样含 Phase 表却未登记。
3. **根本原因**：登记项由人手写，没有从正文派生，也没有双向完备判据。
4. **影响范围**：新增/移动阶段表不会产生任何红灯，闸门长期给出虚假的「范围一致」结论。
5. **整改方案**：判据从所有 `###` 标题及其下 Phase 行派生应检集合，与登记项按
   `(标题行号, 章节名)` 双向比对；行号漂移同样报红。
6. **验收标准**：漏登记、幻影登记、陈旧行号三类各有用例证明报红；当前 2 个非权威表全部登记。
7. **实际整改**：已修，`non_authoritative_phase_tables` 更新为 2781 / 3275 两条。
8. **整改状态**：`[R-VERIFIED]`。
9. **证据**：`test_phase_map_detects_missing_non_authoritative_registration`、
   `test_phase_map_detects_stale_registry_line`、`test_phase_map_detects_phantom_registry_entry`。
10. **残余**：若基线把阶段表改成非 Markdown 表格，解析器会报红而非静默通过，属可接受的 fail-closed。

### A-008 基线冻结状态存在两处互相冲突的权威陈述

`[A-NONCOMPLIANT][P2-MEDIUM][IR-1.3.2-1]`

1. **基准条款**：§31.11「Phase 0 契约冻结状态以文件头部与决议 AFS-P0-FREEZE-2026-11-13-01 为准
   （当前为条件通过），任何章节不得另述冻结状态」。
2. **代码证据**：第 9 行写「冻结已通过（有条件）」，第 17 行写「已通过（条件 C1—C4 已关闭，
   决议已由项目 owner 签署）」；§31.11（3635 行）写「当前为条件通过」，3662 行写「条件通过的修订基线」，
   且两处都自称「以本行/文件头为准，其他章节不得另述」。
3. **根本原因**：一次历史状态升级只改了文件头，未同步修订正文；冻结哈希把两种陈述一起锁死，
   机器判据无法判断哪句有效。
4. **影响范围**：外部评审者无法从仓库内唯一确定 Phase 0 是「已通过」还是「条件通过」，
   而 §31.11 自己规定不得另述——两句都自称权威。
5. **整改方案**：由项目所有者裁定唯一口径，按正式基准修订流程改正文并重签冻结包；AI 不擅自改冻结正文。
6. **验收标准**：全仓库只剩一种冻结状态陈述，且修订台账有对应的已批准条目与签署证据。
7. **实际整改**：未执行（需授权）。
8. **整改状态**：`[R-OPEN]`。
9. **证据**：`docs/baseline/AI影视工业化生产平台V2.0.5.md` 第 9 / 17 / 3635 / 3662 行。
10. **残余**：在裁定前，任何「Phase 0 已完全通过」的表述都缺权威依据；本报告采用保守口径。

### A-009 修订可追溯债务仍有 21 条（承接首次审计）

`[A-PARTIAL][P2-MEDIUM][IR-1.3.2-3]`

1. **基准条款**：修订台账头部「每条修订必须给 source_commits」。
2. **代码证据**：23 条修订中 21 条在 `traceability_debt` 显式挂账；判据双向校验，无法用它放松标准。
3. **根本原因**：历史修订发生时未记录落地提交。
4. **影响范围**：这 21 条修订无法从台账直接定位到提交，只能靠正文与 ADR 间接追溯。
5. **整改方案**：逐条补真实提交 SHA，补一条删一条债务条目（陈旧债务同样报红）。
6. **验收标准**：`traceability_debt` 为空且 `freeze_manifest --check` 仍 PASS。
7. **实际整改**：本轮未补（无可靠历史提交映射，不猜）。
8. **整改状态**：`[R-DEFERRED]`。
9. **证据**：C2.2 / C2.3；`tests/unit/test_freeze_manifest.py` 双向债务用例。
10. **残余**：债务是显式、可枚举、可收敛的，不是隐藏缺口。

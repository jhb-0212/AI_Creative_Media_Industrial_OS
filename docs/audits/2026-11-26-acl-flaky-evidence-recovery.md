## 5. 为什么仍是 BLOCKED

缺的只有一样东西，但它是**决定性的**：**事件 C 的断言正文**。

原用例的判据是：

```python
assert granted == expected, f"{table} 授权口径不符：实际 {sorted(granted)}，期望 {sorted(expected)}"
```

只有正文里的 `实际 [...]` 才能区分三种成因，而三者指向完全不同的整改方向：

| 失败形态 | 含义 | 指向 |
|---|---|---|
| `实际 []` | 该次运行**看不见**任何授权行 | 观察者身份 / 可见性问题（判据缺陷，非授权缺陷） |
| `实际` 少于期望 | 确实少授 | 迁移未生效 / 部分 GRANT 丢失 |
| `实际` 多于期望 | 确实多授 | 越权授予（ACL 漂移） |

三种形态的诊断含义互斥。没有正文就无法排除任何一种，因此**不能宣称根因已定位**。

补充一个本轮核实到的事实（**仅作事实记录，不作根因**）：原判据查询的是
`information_schema.role_table_grants`，该视图只返回 **grantor 或 grantee 属于当前启用角色**
的行，因此其返回结果**含观察者依赖**；`c122daf` 之后使用的 `pg_class.relacl` +
`aclexplode` 直接读 catalog，**不含**观察者依赖。这条差异解释了「为什么替换后的判据更稳定」，
但**不能反推**当日那次失败就是可见性问题——那需要断言正文，而正文缺失。

## 6. 待调查假设（**未验证，不得当作结论**）

按裁决，「记录之外的状态变化」只能作为**待调查假设**保留，禁止升级为已确认根因。

**H1（主假设）｜记录之外的状态变化。**
事件 C 期间，被测库或连接身份被**本会话记录之外**的主体改变。可能来源包括：人工操作
（未落在会话里的终端/客户端）、容器内其它会话、未记录的工具或脚本。
**为何未被排除**：本轮只能检索本机会话转录，无法证明「机器上不存在其它操作者」。
**需什么才能验证**：PostgreSQL 服务端日志（`log_statement` / `log_connections`）或当时的连接快照，
二者当前均未留存。

**H2（H1 的分支）｜观察者可见性瞬变。**
若 `admin_engine` 当次取到的连接处于非预期身份（例如池内连接在前序用例中残留状态），
`information_schema.role_table_grants` 会少返回到「实际 `[]`」。
**已做的排除**：全仓 `tests/` 无 `SET ROLE` / 会话授权切换；但**不能**排除非代码路径的外部操作。
**为何未验证**：按裁决不做历史状态重放；且即便重放，也无法还原当时未记录的外部状态。

**H3｜判据与矩阵在那一刻的期望值不同步。**
`17:17:44` 刚改过 `db_grants.py`。**已排除为主要原因**：同一改动下重跑 4 次全绿（见 §3.4 第 1 条）。

上述三条中，只有 H1 能解释「同输入不同结果」；H2 需要 H1 提供来源；H3 已被时间序列否定。
但**H1 缺少服务端侧证据**，因此整体维持 BLOCKED。

## 7. 与 `c122daf` 的关系

`c122daf` 删除了 `test_append_only_tables_reject_row_mutation`，并把授权对账扩展为
**表级 + 列级 + 角色继承**三路（同一份 `db_grants` 矩阵驱动）。由此产生两个必须分开陈述的结论：

1. **该症状已不可达**：原用例不存在，原形态的红不会再出现。这是「问题消失」，不是「问题解决」。
2. **原用例的判据本身有已知弱点**：它硬编码期望值、且依赖观察者可见的
   `information_schema.role_table_grants`。这两点都在替换后的判据里被消除。

**但这不构成对事件 C 的解释。** `c122daf` 是一个独立的技术决定（判据应归属单一事实源），
它恰好让原形态不再出现；把它当成本次红灯的根因，属事后归因，本记录拒绝这样做。

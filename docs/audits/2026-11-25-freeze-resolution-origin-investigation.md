> 结论先行：**候选原件找到了**，就在同一台机器的项目工作区（仓库外），三份配套文件的时间与
> 内容自洽，且与仓库内契约状态对得上。但「找到文件」不等于「原件已入仓」，更不等于可以解除
> `V-BLOCK-ORIGINAL-FREEZE-RESOLUTION`——**入仓还是定外部权威，是 Owner 的决定**。

## 1. 缺口到底是什么

此前所有记录都写「引用 17 处、原件 0 份」，容易被读成「原件从来没有过」。准确说法是：

- 决议 `AFS-P0-FREEZE-2026-11-13-01` 被基线头部、`§31.11` 与多份审计反复当作最高权威；
- **仓库内确实一份都没有**——`git log --all --diff-filter=A` 遍历全部增删文件，从未出现过以
  该编号或「冻结评审决议」命名的文件；
- 但它并非不存在，而是**从未入仓**：它躺在仓库的父目录里，游离于版本控制之外。

这两件事的处置完全不同：前者需要「补写一份」，后者需要「确认这份是不是那份，并决定它归谁管」。

## 4. 核不了的部分（必须写明，否则这份记录会变成新的乐观来源）

1. **决议所封的那一版基线，没法复核。** 决议抬头写着评审对象是 468816 字节、
   SHA-256 `66ec66d8b047d92f714f6bfa1d6412f9f72c3d19eee23d90331d2e2415a80082` 的基线。
   这个大小与哈希在**本机磁盘与 git 全历史中都不存在**：
   - git 历史里最接近的是 490050 字节的 R14 游离副本（已归档移除）与 489580 字节的 R15 权威基线；
   - 按字节精确检索整个项目工作区，无 468816 字节的文件。
   也就是说：原件说它封了某一版，而那一版已经不在任何人手上。这不影响决议本身的效力，
   但**「冻结哈希可复核」这条链在这里是断的**，不能再宣称「十一类产物哈希一致」等于
   「2026-11-13 冻结的哈希一致」——两者封的不是同一版文件。
2. **文件不能自证。** 它是纯 Markdown，没有数字签名；`mtime` 可以被任何工具改写。
   能支撑它的只有：与 11-22 审计的独立描述吻合、与仓库契约状态吻合、三份文件时间序列自洽。
   这是「高度可信的旁证」，不是「密码学证明」。
3. **因此「找到」不等于「解除」。** 判据上这是两件事：内容存在性（已满足）与权威性归属
   （仍待 Owner）。清单的 `unblocks_when` 写的也正是这两条路径，一条都没被自动满足。

## 5. 两条路径的具体做法（Owner 二选一）

### 路径 A：入仓并登记为冻结面的一部分

1. 原样复制到 `docs/baseline/Phase0-冻结评审决议.md`（**保留原名**，不另起第三个名字）；
2. `contracts/phase0/phase0_manifest.md` 增加条目（字节 + SHA-256 + 校验命令），冻结修订 52 → 53；
3. 台账登记一条修订（`source_commits` 指向本次提交，`approved_at` 取决议日 2026-11-13、
   `recorded_at` 取登记日）；
4. 清单条目改 `LIFTED` + `lifted_scope: ALL`。

代价要说清：**冻结面从此多一份 21KB 的治理文档**，以后每次冻结校验都会覆盖它；而且它进入仓库后，
「原件」与「登记件」就合为一体，再出问题只能靠 git 历史追。

### 路径 B：指定项目外存档为权威，仓库内不再持有原件

1. 在本目录追加一节声明：「以项目外存档为权威、仓库内不再持有原件」，并给出可核验凭据
   （本记录 §2 的路径 + 字节 + SHA-256）；
2. 清单条目改 `LIFTED` + `lifted_scope: ALL`。

代价同样要说清：**任何 clone 这个仓库的人都拿不到原件**，只能读到「哈希是这个」。
这在治理上是可以接受的（很多组织的签署件本来就不入库），但必须由 Owner 明确认下这句话，
而不是由复核方替他默认。

### 路径 C：暂不处置

保持 `BLOCKED`。这是当前状态，不是失败——但下一次对外表述仍须写「条件通过、原件不在仓库」，
不得因为「我们其实找到过」就省略。

## 0. 结论摘要

**标注体系可用，但 Phase 1 不能宣布验收。**

冻结、契约、迁移与静态闸门在这一刻是真实的绿灯：基线正文哈希与冻结登记一致、11 类产物哈希一致、

1. **端到端主链没有串起来**（A-003）。`tests/e2e` 只覆盖项目→剧本→资产→QC→审批的已实现段；
   拆镜→ShotSpec→ConstraintPack→生成路线这一段只有逐域用例，没有跨域链路证明。
2. **实现覆盖是 35/56**（A-004）。ACTIVE 动作 56 个，已实现 35 个，21 个登记未实现；
   转移入口仍有 3 条边逐边登记债务。这些是**已登记的阶段性缺口**，不是隐瞒的故障，但仍是缺口。
3. **生产就绪无证据**（A-005）。没有压测报告、长稳记录、真实第三方模型调用或独立安全验收。

首次取证还发现一个真实的治理缺陷并已根治：**修订台账自称 `source_commits` 必填，
判据里却没有这个字段**，22 条修订用空列表冒充已追溯而全部闸门绿灯（A-001）。
这恰好证明规范的必要性——「文档写了」与「机器执行」是两回事。

## 2. 审计发现

### A-001 修订台账的必填规则只在注释里，判据里少一项

`[A-NONCOMPLIANT][P2-MEDIUM][IR-1.3.2-3]`

1. **编号**：A-001
2. **审计结论**：`[A-NONCOMPLIANT]`——同一条规则在 YAML 注释与 Python 常量各写一份，且实现与声明不一致。
3. **严重程度**：`[P2-MEDIUM]`——不破坏运行时安全，但切断了修订→落地提交的可追溯链，且所有闸门绿灯。
4. **基准条款**：§1.3.2-3「禁止补丁式演进」；`contract_amendments.yaml` 原写入口径第 2 条。
5. **工程铁律**：`[IR-1.3.2-3]`。
6. **实际证据**：台账头部原写「每条修订必须给 id/title/reason/adr/source_commits/approved_by/approved_at，缺一项即 FAIL」；
   而 `scripts/freeze_manifest.py::_REQUIRED_AMENDMENT_FIELDS` 只有 5 项，无 `source_commits`；
   实测 23 条修订中 22 条为 `source_commits: []`，`freeze_manifest --check` 仍 PASS。
7. **根本原因**：规则有两个载体（注释 + 常量），且判空用 `str(value or "").strip()`——
   空列表经 `str([])` 变成 `"[]"`（非空字符串），于是「空清单」被当作「已追溯」。两处维护 + 错误判空，缺一不会出问题。
8. **影响范围**：Phase 0 之后 21 条修订无法指出落地提交；新增修订可以继续用空列表通过闸门。
9. **系统性整改**：判据补 `source_commits`；新增 `_is_filled()` 做结构化判空；
   历史缺口不靠事后编造提交号补齐，而是 `traceability_debt` 显式挂账 21 条并**双向校验**
   （缺了没登记→红，登记了却已补齐→红）；台账头部改为指向唯一权威常量，不再复制字段清单；
   A23 填上真实落地提交 `8f5033b`。
10. **验收标准**：空列表 / 空白字符串 / 未登记债务 / 陈旧债务 / 借债务豁免其它字段 / 非法债务形态
    六类负向用例全部报可读错误；`freeze_manifest --check` 与 `contract_check` 仍 PASS。

**整改状态**：`[R-VERIFIED]`——7 项新增用例通过；`freeze_manifest --check` PASS；
台账实测 21 条债务与实际缺失集合精确相等（C2.2）。

### A-002 仓库自述文档滞后于实现

`[A-OPTIMIZE][P3-LOW][IR-1.3.2-1]`

1. **审计结论**：`[A-OPTIMIZE]`——不改变行为，但自述失准会把审计引向错误范围。
2. **严重程度**：`[P3-LOW]`。
3. **基准条款**：§1.3.2-1（数据归属与边界必须显式定义）；文档导航本身非冻结契约。
4. **工程铁律**：`[IR-1.3.2-1]`。
5. **证据**：`docs/architecture/repository-structure.md` 的 docs 树只列 4 项（还包含不存在的 `sop/`），

   而 A22 / A23 已交付端点与逐域用例。
6. **根本原因**：自述文本靠人工维护、没有从文件系统派生的完备性判据，也没有明确的同步责任人。
7. **影响范围**：审查者按旧自述定位实现范围，会低估已交付面，并把 Phase 1 验收缺口错定位成「未实现」。

9. **验收标准**：`find docs -maxdepth 1 -type d` 与结构树双向一致；README 中提到的测试目录存在。

**整改状态**：`[R-IMPLEMENTED]`——**不标 `[R-VERIFIED]`**：本次是人工修正，根因（无派生判据）仍在，

### A-003 Phase 1 端到端主链未串通

`[A-GAP][P1-HIGH][IR-1.3.2-4]`

1. **审计结论**：`[A-GAP]`——「整体验收证据不足」，不是「整个 Phase 1 没实现」。
2. **严重程度**：`[P1-HIGH]`——关键业务链路没有端到端证明。
3. **基准条款**：`contracts/phases/phase_map.yaml` Phase 1 core_production；§1.3.2-4。
4. **工程铁律**：`[IR-1.3.2-4]`。
5. **证据**：C7.3 真实执行 3 项通过，但用例只走项目→集数→剧本→资产→QC→审批；
   证据文件明确记录限制「剧本→拆镜→ShotSpec→ConstraintPack 这一段由逐域用例证明，端到端链路尚未串起」。
6. **根本原因**：逐环实现与逐环测试先落地，跨环串联没有随每环交付同步补齐；
   端到端用例头部的过期自述（A-002）又让这个缺口在多次审查中被读成「还没实现」，从而错失补齐时机。

8. **系统性整改**：下一环「单一路线生成」落地时，把拆镜→ShotSpec→ConstraintPack→生成路线
   接成一条端到端用例，而不是单独再写一个「链路测试」文件——新增平行测试套件只会多一处要同步。
9. **验收标准**：一条用例内完成上述四环，且中途变更 ConstraintPack 状态能阻止生成（CP-7 升为 `ENFORCED` 的前提）。

**整改状态**：`[R-OPEN]`。

## 6. 本次取证暴露的工具自身缺陷（已修）

为了让「取证工具」本身不制造新的漏检，本轮修了三处：

1. **重复 `-q`**：仓库 `addopts` 已有 `-q`，电池再传一次变成 `-qq`，pytest 不打印统计摘要，
   指标解析全空且被误判成 FAILED。修法：不重复传参；并把「解析不到数字」单独判为 PARTIAL
   （证据不足 ≠ 测试失败），抽成 `_pytest_state()` 纯函数，5 项参数化用例固定语义。
2. **宿主安全钩子**：沙箱拦截 pytest 临时目录清理时会把全绿会话变成非零退出；
   识别 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 标记并判 `V-BLOCKED`，不冤枉代码。
   进一步根治：pytest 改用工作区内固定 `--basetemp`，不再累积 `/tmp/pytest-of-*` 触发批量回收。
3. **手写测试层清单漏了 `tests/architecture`**（4 项测试从未进入核验表）。
   修法：待扫目标从文件系统派生（`_discover_test_targets()`），新增未登记目录即产出 FAILED 探针；
   3 项完备性用例证明「不重复、不遗漏、每目录都有归属层」。这与 A13 的教训一致：
   手写清单的腐烂方向恰好是不安全的一侧——加了目录就是漏检，而漏检表现为绿灯。

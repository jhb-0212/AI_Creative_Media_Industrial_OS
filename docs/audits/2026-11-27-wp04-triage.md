# WP-04 分级证据：22 个 revision 的隔离库往返实测

日期：2026-11-27　方法：每 revision 一个一次性库，父 revision 快照 P → 升级 → 降一级 → 快照 D

## 1. 口径（为什么这是证据而不是推断）

```
P = 父 revision 的 catalog 快照（表/函数/schema ACL + 默认权限 + 角色属性 + 对象存在性）
U = 升级到目标 revision（不取快照，只用于产生差异）
D = 降级回父 revision 后的快照
```

判定：

- **P == D（0 差异）** → 该 revision 的全部撤权动作都是 no-op，不需要恢复 → `no_restore_proven`
- **P != D** → 降级没有回到父态，差异逐条列出 → `restore_required`（真实缺陷，必须修）

差异分四组：`acl`（表/函数/schema ACL、默认权限）、`rels`（对象存在性，含索引）、`funcs`、`roles`。
`pg_toast` 内部的 OID 抖动（表重建导致 toast 表编号变化）已从判定中剔除，避免把抖动当缺陷。

## 3. 这批结论修正了什么

1. **原 9 条 `unproven_blocking` 全部收口**：7 条实测 P==D（no-op），2 条（#35/#37）实测有残留索引 → 真实缺陷。没有"无法证明"项剩下。
2. **13 条 V2 新暴露项也全部收口**：5 条 no-op，8 条真实缺陷（其中 #34/#41 最重）。
3. **"数量相等"之外还漏了结构**：#35/#37 的缺口不是权限，而是降级没删自己建的唯一索引；这类问题只有快照比对能抓到。
4. **#41 的降级会改变表结构**：父态的 `ix_..._gate_key` 消失、出现 `ix_..._project_id_gate_key`，同时表 ACL 比父态多。这是 D-02 修复没有覆盖到的另一半：只处理了索引名比对，没有验证"降级后的索引集与父态一致"。
5. **越权恢复比漏恢复更常见**：#14/#20/#29/#47/#59/#62 都是降级给多了（把父态没有的授权补上）。这类问题在三方 ACL 对比时会被误读成"恢复成功"，必须用 P 与 D 直接比对才能发现。

## 4. 这些差异的性质

| 类型 | 例子 | 风险 |
| --- | --- | --- |
| 结构残留 | #35 #37 #41 | 降级后 schema 与父态不一致，后续迁移/比对失真 |
| 越权恢复 | #14 #20 #29 #47 #59 #62 | 降级把权限放大，安全面回退 |
| 默认权限扩张 | #34 #62 | 新对象继承到不该有的权限 |
| DDL 语义错误 | #41 | 表被重建/索引集改变，可能丢数据 |

# 受控例外实现：把「守卫不可禁用」变成可执行的窄门

> 日期：2026-11-20 ｜ 依据：ADR-R40 v1.4.5 §13 D-10.2 / D-10.2.1 ｜ 授权：所有者「可以」
> 迁移：`data/migrations/pending/feat-ownership/b0c9d8e7f6a5_ownership_repair_exception.py`
> 验证：**36/36 通过**（克隆库，用完即删）

## 1. 一句话结论

D-10 要求「层 1 外键先上、层 2 守卫不得禁用、订正走受控例外」。层 1 已于 `a9b8` 完成，
本轮把**层 2 的受控例外**做成可执行迁移：13 张表的不可变守卫全部接入同一个判定函数，
四条件缺一即拒绝。**验证阶段发现并修掉了一个会让整个例外机制失效的实现缺陷**（见 §3.1）。

## 2. 实现结构

```
c4e5f6a7b8d9（分支链 head）
  └─ a9b8c7d6e5f4  层 1：14 条归属外键 NOT VALID + organizations + 4 个目标键
       └─ b0c9d8e7f6a5  层 2：受控例外（本迁移）
```

| 部件 | 内容 | 为什么这样 |
| --- | --- | --- |
| `ownership_repair_map` | 逐行映射：`table_name / row_key / 新旧归属 / reason / ticket_ref / applied_at` | 例外必须**逐行可审计**，不是「整表放开」 |
| `ownership_repair_map_match()` | `SECURITY DEFINER` 只读映射表 | 业务角色不该有映射表 SELECT（含工单号、运维信息）；提权只发生在这一个只读查询里 |
| `ownership_repair_allows()` | `SECURITY INVOKER` 四条件判定 | **必须 INVOKER**，原因见 §3.1 |
| 13 个守卫 | 原文逐字保留，仅在 `BEGIN` 后注入一段接入 | 原文由 `pg_get_functiondef()` 导出，机器生成、非手抄 |
| `afs_data_repair` | `NOLOGIN` 专用角色 | 只能 `SET ROLE` 进入，不能直接登录 |

四条件（缺一即 `P0001`）：

1. 会话角色是 `afs_data_repair` 成员（`pg_has_role` 读会话真实身份，`SET app.*` 无法伪造）
2. 设置了工单令牌 `app.ownership_repair_ticket`
3. 变更列 ⊆ `{project_id, organization_id, tenant_id}`（**函数自算**，不接受调用方传入）
4. 映射表存在 `(表, 行标识, 工单)` 匹配且 `applied_at IS NULL`

第 3 条刻意不让调用方传「变更列集合」：一旦可传入，调用方就能谎报「我只改了归属列」
而实际同时改内容列，例外立刻变成万能钥匙。这是本轮唯一一处**拒绝便利、换取不可绕过**的设计。

## 3. 验证中发现的三件事（不做端到端就发现不了）

### 3.1 `SECURITY DEFINER` 会让「角色条件」静默失效（严重）

第一版把四条件全写在 `SECURITY DEFINER` 函数里。验证用例 `F8`（非成员调用应返回 false）
**实得 true**。

根因：SECDEF 函数体内 `current_user` 是**函数 owner**（迁移执行者/超级用户），
不是调用者。于是 `pg_has_role(current_user, 'afs_data_repair', 'member')` 恒为真，
条件 1 形同不存在——**任何拥有表写权限的角色都能订正归属**，例外退化为万能钥匙。

修法不是加判断，而是**拆开提权范围**：

| 函数 | 安全模式 | 职责 |
| --- | --- | --- |
| `ownership_repair_map_match` | `SECURITY DEFINER` | 只读映射表（唯一需要提权的事） |
| `ownership_repair_allows` | `SECURITY INVOKER`（默认） | 角色判定 + 令牌 + 变更列校验，全部在调用者上下文 |

拆开后 `F8` 由 `true` 变 `false`，并被固化为结构断言 `S2`（判定函数 `prosecdef` 必须为 false）。

> 这类缺陷不会在任何「结构检查」或「代码 review」里显形：函数能建、能跑、正向用例全绿。
> 只有「以非成员身份执行一次并期望失败」才暴露。这正是 D-10.2.1 义务 2 要求
> 「负向用例逐一被拒才算通过」的现实理由。

### 3.2 RLS 先于守卫生效，会把「越权改归属」变成静默 0 行

`gate_decisions` 启用了 RLS。探针角色（非成员）执行 `UPDATE` 时得到 **`UPDATE 0`**：
行在 RLS 层就被过滤掉，根本没走到守卫。

含义有两面：
- 好的一面：RLS 是一层真实存在的额外防线，越权写者连行都看不见；
- 必须记录的一面：**「没报错」不等于「改成功」**。若验收脚本只看「有没有抛异常」，
  会把 `UPDATE 0` 当作通过——这又是本项目反复出现的真空真陷阱。
  本轮因此把正向用例改为断言 `UPDATE 1` **且回读值确实变了**（`E1/E6/E7`）。

### 3.3 `GRANT UPDATE` 不够，`WHERE` 子句还需要 `SELECT`

只授 `UPDATE` 时，探针执行 `UPDATE ... WHERE entity_id=...` 得到 `42501`。
PostgreSQL 对 `UPDATE` 的 `WHERE` 列读取需要 `SELECT` 权限。

这条对运维是硬输入：**`afs_data_repair` 必须在被订正表上同时具备 `SELECT` 与 `UPDATE`**，
否则订正会在权限层失败，而错误码看起来像「守卫拒绝」，极易误判。

## 5. 范围与刻意的取舍

**13 张表** = 归属矩阵中有不可变守卫的全部域表 + `asset_versions`（第 15 张，T3 代表表）
+ `qc_reports`（有归属列但无 `entity_id`，键列是 `qc_report_id`）。

刻意**不做**的三件事：

| 不做 | 理由 |
| --- | --- |
| 不抽「逐列不可变」公共骨架 | 8 个逐列型守卫的可变列白名单各不相同（`approved_by`/`lease_*`/`locked_*`…），抽骨架等于重写 13 个函数，风险远大于收益。本轮只把**例外判定**收敛为唯一实现，登记重复逻辑为既有债务 |
| 不 `GRANT` 表权限给 `afs_data_repair` | 订正执行者是否表 owner 属运维决策，迁移不该替人决定。已写入 README 作为激活前置 |
| 不删 `afs_data_repair` 角色（降级时） | 角色是集群级对象，其他库可能已依赖；删角色会引发 `REASSIGN` 需求。保留一个 NOLOGIN 无授权空角色是安全的 |

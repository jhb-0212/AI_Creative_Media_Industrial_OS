# 约束来源标记的兼容性契约（#35 / #37）

- 日期：2026-11-27
- 适用：`packages/shared/migration_constraints.py`、`a13b0c1d2e3f`、`c3d4e5f6a7b8`
- 性质：**兼容性契约**，不是实现说明。任何后续改动若违反下列四条，视为破坏契约。

## 契约本体

| 场景 | 规定行为 | 判定依据 |
|---|---|---|
| 新建数据库 | 升级写入标记 `wp04-created-by:<revision>`；降级验证标记存在后准确删除该约束 | `pg_description` + `pg_constraint` 双查，标记相等才 `ALTER TABLE ... DROP CONSTRAINT` |
| 既有数据库（升级发生在引入标记之前） | 约束**没有**标记 → 降级**不删除**，保留对象并 `RAISE NOTICE` 记录"非本 revision 创建" | 标记为 NULL 不进入删除分支 |
| 标记存在但与对象定义不一致 | **阻断**：不得按标记盲删。必须先核对约束列集/唯一性/引用关系，再决定修标记还是修对象 | 人工核对 + 后续新增 `drop_marked_constraint` 的定义校验（当前未实现，见"未实现项"） |
| 保留未标记对象后 | 必须**明确报告降级后的状态差异**（对象名、schema、缺失的 DROP），不得把该次降级报成"完全可逆" | 降级日志里的 `RAISE NOTICE` + 审计快照的 `diff` 记录 |

## 为什么需要这四条

1. `IF EXISTS` 会把"父态本来没有、升级建了、降级漏删"伪装成成功；
2. 无条件 `DROP CONSTRAINT` 会把父态真实存在的对象删掉（方向相反的破坏）；
3. 标记是"来源证据"，不是"所有权证明"——标记与定义不一致时，说明迁移文本与库状态已经分叉；
4. 保守保留会让 D ≠ P，这种不相等必须被**说出来**，否则闸门会把"少删"当"可逆"。

## 未实现项（必须承认的边界）

- 当前 `drop_marked_constraint` 只校验**标记字符串**，没有校验"标记指向的对象定义是否仍与升级时一致"（列集、唯一性、引用）。若要满足第三条的强形式，需在 helper 里补一段 catalog 校验 SQL，并在不一致时 `RAISE EXCEPTION`。
- 既有库（无标记）执行降级时，triage 快照会看到残留约束并判 `restore_required`；这属于**预期差异**，应按"老库数据修复流程"单独处理，不能靠重跑迁移自动消失。

## 回归

`tests/unit/test_migration_constraint_contract.py` 固化本契约的四个可机读点：
辅助模块不执行 DDL、标记可被 `pg_description` 查询、未标记走保留分支、迁移显式 `op.execute`。

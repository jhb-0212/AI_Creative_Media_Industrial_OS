## 2. 复核项一：分叉统计口径（两个口径，不是把 3 改成 10）

所有者指出：**Revision ID 冲突数量与跨分支文件分叉数量不是同一个指标**，不能把原文的「3 个迁移冲突」
直接改成「10 个迁移冲突」。这个判断是对的。实测后可以给出三个互不替代的口径：

### 2.1 三个口径的定义与实测值

| 口径 | 定义（判定单元） | 实测值 | 用途 |
| --- | --- | --- | --- |
| **A. 迁移身份冲突** | 同一个 Revision ID 在两侧被**不同内容**的文件定义 | **10** | 判断 Alembic 迁移图能否直接拼接（Alembic 只比 ID，不比内容，故这 10 个它全部「无感」） |
| **B. 跨分支分歧项** | 经「路径 + 内容哈希 + 归一化文本」确认的**独立决策单元** | **10** = T1×1 + T2×7 + T3×1 + T4×1 | 判断逐项裁决的工作量（每一类要不同的裁定方式） |
| **C. 语义不等价冲突** | 归一化掉「角色名来源」后**仍有实质差异**的分歧项 | **3** = `b3c4` + `9e3b` + `b7c8` | 判断哪些项**必须**逐句读、不能靠等价性推断放行 |

> 口径 A 与 B 数值恰好都是 10，但**成员与判据完全不同**，是两个指标：
> A 的关键是「ID 相同、内容不同」；B 的关键是「决策单元」。数值相同纯属巧合，
> 文档中必须并列呈现，不得合并成一个「10 个冲突」。

### 2.2 ADR 现状与缺陷

ADR 附录 C.1（第 1087~1100 行）只登记 **3 个 Revision**（`b3c4` / `b7c8` / `9e3b`），
并在第 1099 行称其为「『同 Revision ID、不同迁移内容』的硬证据」。

这里存在**标签与口径不符**：

- 按字面定义（ID 相同、内容不同），实测是 **10** 个，不是 3 个——ADR 漏了 7 个；
- 但被登记的这 3 个，恰好等于**口径 C 的 3 个语义不等价项**；
- 也就是说：**ADR 的成员选对了，标签写错了**。它记的是「必须逐句裁决的 3 项」，
  却称自己记的是「同 ID 不同内容的全部」。

这个区分不是文字游戏，它决定了后续两件事的判断：

1. 若按 ADR 现文字理解「只有 3 处内容不同」→ 会低估迁移图拼接风险（另 7 处虽在默认配置下等价，
   但**一旦部署侧改过 `POSTGRES_APP_USER`，7 处同时变成真实角色名分叉**）；
2. 若把 3 直接改成 10 → 会高估裁决工作量（7 处并不需要逐项业务裁定，只需一条配置约束）。

### 2.3 口径 B 的机器验证（不是人工分类）

「7 处只差角色名来源」此前是**断言**。本轮改为**可复现的机器验证**：
把两侧源码的角色名表达式归一化为同一占位符，剔除仅由「角色名来源」引起的形式差异
（导入行、常量定义行、空行），再用 `difflib` 序列比对。

归一化规则（`docs/audits/mig-recon/verify_t2_equivalence.py`）：
`app_role_name()` → `ROLE_NAME`；`APP_ROLE` / `_APP_ROLE` → `ROLE_NAME`；
`ROLE_NAME = "app_role"` 定义行删除；`from packages.shared.db_roles import ...` 删除；空行删除。

### 2.4 三类残差的具体内容（逐条读过的结论）

**T3 `9e3b`（20 行残差）—— 两处真实语义差异**：

| 项 | main | 分支 | 后果 |
| --- | --- | --- | --- |
| 已存在角色的属性 | `ALTER ROLE … WITH LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS PASSWORD '…'` | `ALTER ROLE … WITH PASSWORD '…'` | 分支**不收敛**既有角色的 `BYPASSRLS`。RLS 对 `BYPASSRLS` 角色不生效 → 这直接决定数据库还是不是隔离边界 |
| 开发默认口令守卫 | 调 `reject_development_default_password(settings, …)` | 无此调用 | 分支允许以开发默认口令建角色 |

两侧 `CREATE ROLE` 分支**完全相同**，差异只在 `ALTER` 路径。
⇒ 在**干净集群**上（角色不存在）该差异不可观测，这是本次实验的方法论限制，不是遗漏（详见 §2.6）。

**T4 `b7c8`（7 行残差）—— 调用点绑定，效果同、组合不兼容**：

```
- for statement in protect_partition_statements(partition):
+ for statement in protect_partition_statements(partition, roles=(ROLE_NAME,))
```

两侧 `packages/shared/partition_guard.py` 的签名不同（main `role=None` / feat `roles=Sequence[str]` 必填），
因此**迁移与 helper 必须成对取用**，交叉组合会 `TypeError`。这是**组合约束**，不是效果差异。

**T1 `b3c4`（292 行残差）—— 两个不同功能**：

main 是「资产归属项目 + 跨 schema 复合外键」，分支是「状态只能沿已登记边推进（状态机守卫）」。
两者**解决的问题不同、对象不同、可以共存**，不构成二选一。

> 这一点与审查报告的表述有出入：报告称分支 `b3c4` 建立「状态转移事实表」。
> 实测分支建的是 `asset_service.asset_status_transitions` 等 6 张 `(from_status, to_status)` **规则登记表**
> （播种「哪些转移合法」），而「发生过什么转移」的**事实表**是 main 的 `audit.status_transitions`。
> 两者是不同性质的表，这也正面支持「用唯一新 Revision 前向补齐」而非二选一。

### 2.5 v1.4.3 应采取的形式

不建议把 C.1 的 3 改成 10，也不建议保留 3 而不解释。建议：

1. C.1 标题与导语改为「**必须逐句裁决的语义不等价冲突（口径 C）**」，明确写出「全量内容分叉 10 个见附录 C.1.1」；
2. 新增 **C.1.1 全量分叉清单**（10 行，五列：Revision / 类型 / 两侧 blob / 两侧 SHA-256 / 归一化残差）；
3. 新增一段**口径定义**（口径 A/B/C 三行表），明确「三个数字不可互换」；
4. 明确 T2 的**前置条件**：等价性成立的前提是 `POSTGRES_APP_USER` 保持默认值 `app_role`；
   一旦部署侧改过该变量，7 个 T2 立即变成真实角色名分叉，须重新裁决。

### 2.6 关于 T3 的可观测性限制（必须先说清）

T3 的差异只出现在 `ALTER ROLE` 路径，而干净集群上角色由 `CREATE ROLE` 建立，`ALTER` 分支不执行。
因此：

- 「T3 效果不等价」这一结论，**来源是源码逐句比对 + PostgreSQL 语义**，不是本轮实验证明的；
- 要实验验证，必须构造 `BYPASSRLS=true` 的脏前置状态（先手工 `ALTER ROLE … BYPASSRLS`，再跑该迁移）；
- 本轮**未做**此项，列为可选验证（与 T3 归属实验是两件不同的事，不要混淆）。

## 3. 复核项二：哈希清单（双锚点 + 固定来源）

### 3.1 ADR C.1 的实测缺陷：SHA-256 混用两种口径

对 C.1 的 6 行逐一重算，**按四种候选口径**（LF 原样 / CRLF / 去尾换行 / git blob 头）比对：

| Revision | 侧 | ADR 声称 SHA-256 | 匹配口径 | LF 实际值 |
| --- | --- | --- | --- | --- |
| `b3c4d5e6f7a8` | main | `fbc0da26…` | LF 原样 ✓ | 一致 |
| `b3c4d5e6f7a8` | 分支 | `0d1c44d2…` | LF 原样 ✓ | 一致 |
| `b7c8d9e0f1a2` | main | `7af954b5…` | **CRLF** ✗ | `0caf8be5…` |
| `b7c8d9e0f1a2` | 分支 | `2a8d7d23…` | LF 原样 ✓ | 一致 |
| `9e3b4c5d6e7f` | main | `0dd3d2fd…` | **CRLF** ✗ | `76e33051…` |
| `9e3b4c5d6e7f` | 分支 | `57c3d775…` | LF 原样 ✓ | 一致 |

**根因**：同一张表里 2 行按 CRLF 计算、4 行按 LF 计算。这不会在阅读时暴露，
但只要有人按表复核，这 2 行必然「对不上」——而复核者无法判断是「文档错」还是「文件被改」。

**一个反直觉但重要的事实**：C.1 的 **git blob 列 6 行全部准确**（已用 `git rev-parse <ref>:<path>` 逐一验证）。

> 这说明 **git blob SHA1 才是稳定锚点**：它由 Git 对仓库内字节计算，不受工作区 `core.autocrlf` 影响；
> 而文件 SHA-256 依赖「你怎么取字节」。建议 v1.4.3 把主锚点改为 blob SHA1，SHA-256 降为辅助列
> 并显式标注「口径：`git show <ref>:<path>` 原始字节（LF）」。

## 4. 复核项三：§7.0.4 的位置

### 4.1 事实

| 项 | 实测 |
| --- | --- |
| 正文是否存在 | **存在**，第 723 行 |
| 标题形式 | `**7.0.4 DROP 前的跨库依赖验收（v1.4.2 新增，PostgreSQL Role 是集群级对象）**` —— **加粗段落**，不是 `###` 标题 |
| 章节物理顺序 | `7.0.1`（705）→ `7.0.2`（714~721）→ **`7.0.4`（723~753）** → `7.0.3`（755~760） |

### 4.2 为什么这会被判成「条款不存在」

两个叠加原因，任一条都足以让复审者找不到：

1. **不是 Markdown 标题**：`grep "^### 7\.0"` 或目录树都扫不到它，只有 `grep "^\*\*7\.0\.4"` 能找到；
2. **序号倒序**：读者按 7.0.1 → 7.0.2 → 7.0.3 顺序读，读到 7.0.3 就以为 §7.0 结束，
   而 7.0.4 夹在 7.0.2 与 7.0.3 之间，**既不在开头也不在结尾**，最容易被跳过。

这不是「条款缺失」，是**排版导致的可检索性缺陷**。所有者手上的 `(2)` 版本更早，
但即使拿到 v1.4.2，按序号顺序阅读同样会漏。

### 4.3 归位方案（建议，未执行）

**不采纳「把编号改成 7.0.3、原 7.0.3 改 7.0.4」**。先给出引用的真实分布（实测，不是估计）：

| 引用 §7.0.4 编号的位置 | 处数 |
| --- | --- |
| 版本表（第 25 行） | 1 |
| 附录 H · H8（第 2501 行，「落点」列写 `§7.0.4（新增）`） | 1 |
| 合计 | **2** |

也就是说，显式按编号引用只有 2 处，改编号的破坏面**比我上一轮估计的小**。
但仍不建议改编号，理由是：H8 是「第五轮问题落实矩阵」的一行，复审者会拿它对照 ADR 正文；
一旦编号错位，矩阵与正文的对应关系失效，而**这种失效不会报错**，只会让复核静默错位。
保留编号 + 改标题层级 + 移位置，成本更低、风险更小。

建议**保留编号 `7.0.4` 不动**，只做两件事：

1. 把 `**7.0.4 …**` 改为 `### 7.0.4 …`（与 7.0.1~7.0.3 的 `**…**` 形式统一——注意
   7.0.1~7.0.3 也是加粗段落，所以**要么全部升级为标题，要么全部保持**；建议**全部升级为 `###`**，
   这样 §7.0 四级编号可被目录与搜索定位，且不改变任何编号）；
2. 物理移动到 `7.0.3` 之后，使顺序为 7.0.1 → 7.0.2 → 7.0.3 → 7.0.4。

**影响面**：编号不变 ⇒ 所有交叉引用保持有效；仅位置与标题层级变化 ⇒ 目录与检索变正确。
这是「不改语义、只改可检索性」的最小改动。

## 5. 复核项四（本轮新发现）：版本标注覆盖率不足

ADR 第 30~31 行声明：**「新增/修订内容以 `【v1.4】` / `【v1.4.1】` / `【v1.4.2】` 标注」**。

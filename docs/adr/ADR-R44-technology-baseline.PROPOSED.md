## 1. Why（为什么需要这份 ADR）

方案把若干候选技术写进"推荐目标架构表"，同时又声明"尚需 Owner 正式批准技术 ADR、不把候选当已批准生产依赖"。当前仓库与方案之间存在**会改变执行模型和数据权威的分歧**：若实现方据方案表直接引入 Temporal / PostgreSQL 18 / Valkey / S3，会在没有裁决的情况下制造第二套长流程执行引擎、触发全链 RLS/分区复验、改变限流故障语义、并迫使 `local://` 定位器契约重签。

根因不是"选哪个组件更好"，而是**"目标架构表"没有权威状态标记**：候选与已批准在一份文档里同形同列，读者无法分辨。本 ADR 的职责是把每项技术的状态显式化（已批准现状 / 候选待 PoC / 冲突待裁决），并锁定裁决前的行为——**维持现状**。它不负责替 Owner 做选择。

## 2. 决策（本 ADR 实际裁定的内容）

| 编号 | 裁定 | 性质 |
|---|---|---|

| D2 | 裁决前，仓库**维持现状**：PostgreSQL 16、Redis 7、`local://` 内容寻址、Outbox Saga 长流程、无 Temporal 服务 | 冻结现状裁定（可执行） |
| D3 | 五项技术分歧（§3）全部标记为 **BLOCKED，需 Owner 逐项裁决**；实现方不得自行采纳方案表中的任何候选 | 治理裁定（可执行） |
| D4 | 方案中与既有铁律**同向**的原则（ADR/契约冻结、事实单源、资产不可覆盖、终态不可复活、审计与补偿、Agent 不越权、验收四态）直接继承，不新立平行规范 | 继承裁定（可执行） |

## 4. 与既有 ADR / 基线的关系

- **不覆盖**：本 ADR 不改变 R42（Saga 已 DECIDED）、R43（画布边界已 DECIDED）、R40（授权模型 PROPOSED，阶段 3 不放行）的任何结论。TC-1 若选 (c)，须走 R42 的正式修订流程，而非本草案直接改写。
- **不新立规范**：D4 继承的治理原则其权威仍在 V2.0.5 与已批准 ADR；本 ADR 不定义第二套铁律编号（遵循 `docs/standards/verification-and-audit-annotation-standard.md` §2.3 对自造 IR 编号的禁令）。
- **证据时效**：本 ADR 引用的对账报告是 main @ `abf77c18…` 的时点判断；基线推进后须重新对账，不得沿用本报告结论充当新 SHA 的事实。

## 5. 后果

**正面**：把"目标架构表里的候选"与"已批准现状"分开，堵住实现方据蓝图直接引入组件的路径；把会改变执行模型/数据权威的五项分歧集中到一处等待裁决；给出统一的裁决门槛。

**代价**：阶段 B 的基础设施升级在裁决前不启动；PG18/Valkey/S3/Temporal 的潜在收益延后。这是刻意接受的——先守住单一事实源与冻结治理，再谈组件升级。

**风险**：若有人把本草案的"候选选项"误读为"已批准可实施"，会同时破坏 D2/D3/D5 与冻结清单。判据是：§3 任一 TC 的"Owner 裁决记录"栏未填且未走冻结重签而现状已变，即视为违反本 ADR。

本 ADR 目前为草案。仅在以下条件全部满足后才转为 DECIDED：

1. Owner 对 §3 五项 TC 逐项签署裁决（填入裁决栏）；

3. 对账报告以当期 main SHA 重出，确认无新增冲突；
4. 若裁决涉及契约/迁移变更，冻结清单重签完成。

## 1. 问题

当前降级链在真实 PostgreSQL 上的失败有三种完全不同的性质，混在一起讨论会导致错误策略：

| 现象 | 例子 | 性质 |
| --- | --- | --- |
| 对象名算错 | `f9a0b1c2d3e4` 按错名字 `DROP INDEX`（D-02） | 代码缺陷，必须修 |
| 跨 revision 的依赖顺序 | `c1a2b3d4e5f6` 降级去 `REVOKE` 更晚才建的表（D-07） | 代码缺陷，必须修 |
| 数据不满足前置条件 | `e1f2a3b4c5d6` 的 `ck_generation_tasks_status` `VALIDATE` 失败 | **策略**：这是设计意图 |

第三种如果被描述成"有数据就拒绝降级"，就会得到一条宽到无用的规则：任何有业务数据的库都不能降级；也会得到一条窄到危险的规则：把守卫当成"测试环境才有的偶发失败"，然后加个跳过。两种都错。

**正确原则：仅当某个 revision 的明确数据前置条件不满足时，才拒绝降级。** 没有数据约束的 revision，即使表里有数据，只要结构操作安全，就应当允许降级。

## 2. 分类模型（六类，必须逐 revision 显式归类）

| 类别 | 判定 | 降级规则 | 失败行为 |
| --- | --- | --- | --- |
| A. 无数据要求 | 只做结构/权限/索引操作，降级不依赖行状态 | 允许自动降级 | 结构失败即报错回滚 |
| B. 数据前置条件 | 降级需要有明确状态的行满足某约束（如"不存在 `AWAITING_ASSET_REGISTRATION` 在途行"） | 必须先通过条件检查 | 检查失败 → 事务内拒绝，错误信息给出条数 |
| C. 任务静默条件 | 降级会与在途任务竞争（outbox 投递、重放、生成任务） | 先停新增任务、处理在途，再降级 | 未静默 → 拒绝并列出在途记录 |
| D. 可逆数据转换 | 降级需要把数据反变换回旧语义（如状态合并/拆分） | 必须证明反变换可恢复原语义 | 无法证明 → 降级 |
| E. 有损数据变更 | 降级会丢失列/行/精度 | 需要数据保全（备份表/导出）+ 审批 | 无保全方案 → 拒绝自动降级 |
| F. 不可逆变更 | 信息在升级时已永久丢失 | **明确标记不支持自动降级** | 禁止伪装成可逆；只允许重建或前滚 |

归类是**声明**，不是推断：每个 revision 在清单里写明类别与依据；清单由 inventory（语句级事实）生成后人工复核，不允许"看起来没事"就默认 A。

## 3. 守卫位置：必须在破坏性 DDL 之前

执行顺序硬约束：

1. 进入降级事务；
2. **先执行该 revision 的数据守卫**（只读查询，`SELECT`/`COUNT`）；
3. 守卫通过后才执行 `DROP`/`ALTER`/`DELETE` 等破坏性语句；
4. 守卫失败 → 在事务内 `RAISE EXCEPTION` → 整条降级回滚，`alembic_version` 不变。

禁止的形态（本轮已实测到的反例）：

- 先 `DROP COLUMN` 再在后续步骤 `VALIDATE` 才发现数据不满足——已经丢了列；
- 用 `IF EXISTS` / `ON CONFLICT DO NOTHING` 把守卫失败变成"跳过"；
- 把守卫写成迁移注释或运维手册，代码里没有检查；
- 让守卫依赖执行人记得先手工清数据（那不是守卫，是口头约定）。

守卫必须是**迁移内的 SQL 检查 + 明确的失败语义**，或者由迁移调用的共享 helper（同一份实现，便于加测试），不能是外部脚本。

## 4. 清单契约（生成物 + 人工复核；当前版本见 `docs/audits/2026-11-27-identity-migration-inventory.json`）

每条 revision 至少包含：

- `revision` / `down_revision` / 简述；
- 升级动作、降级动作（语句级，来自 inventory 的 `rows`）；
- 影响的表 / 索引 / 约束 / 记录 / 状态；
- 数据前置条件（可为空）；
- 条件检查方式（具体 SQL 或 helper 名）；
- 条件不满足时的失败行为（异常类型、错误信息要点、退出码）；
- 是否允许自动降级（`auto` / `guarded` / `manual` / `unsupported`）；
- 回滚与数据恢复方案（备份对象、恢复步骤）；
- 对应测试证据（测试文件 + 场景名）。

清单是**生成物 + 人工复核结论**的组合：生成物提供语句事实，类别与"是否允许自动降级"必须有人签字。

清单来源与边界：inventory 由当前 HEAD 的迁移源码重新生成，元数据记录 `head_sha`、`generated_at`、生成工具与扫描范围；语句由静态展开得到，展开失败的语句记入 `expansion_failures` 并标 `UNPROVEN`，不得视为完整覆盖。生成后执行敏感信息扫描，明文口令、连接凭据与可复用密钥一律擦除后才允许归档。

## 5. 测试要求（每类都要有）

三类数据场景，缺一不可：

1. **符合条件的数据**：降级成功，降级后状态与旧 revision 定义一致；再升级回 head 无差异。
2. **违反条件的数据**：降级失败，且失败后 `alembic_version` 仍为原 revision、目标表/索引/约束完好、无半完成残留（用 catalog 查询证明，不是看日志）。
3. **边界状态数据**：空表、恰好满足条件的单行、NULL 与默认值混用。

另外两条通用断言：

- 守卫失败时**不得**出现"部分降级"（比较失败前后 `pg_class`/`pg_index`/`pg_constraint` 快照）；
- 守卫不得在破坏性 DDL 之后执行（用 `_OpRecorder` 类打桩断言调用顺序）。

## 6. 后果

- 需要新增：迁移级 `assert_data_precondition(...)` helper（与 `migration_identity` 同层，显式传 `op` 以便门禁回放）、清单 schema、矩阵脚本读取清单。
- 需要修改：`e1f2a3b4c5d6` 等已有守卫从"隐式 VALIDATE 失败"改为"显式守卫 + 明确错误信息"（不改变语义，只让失败可读、可测试）。
- **不做**：通用迁移框架、运行时自动修复、按“有数据”整体拒绝降级、用 `IF EXISTS` 掩盖、把守卫放在 `VALIDATE` 之后。
- 本轮边界：实现与隔离库全链验证**已完成**（WP-A #41、WP-B 单轮、WP-C 连续三轮）；正式环境迁移、提交发布与部署**不在本 ADR 范围**，且尚未执行。

## 7. 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| "表里有数据就拒绝降级" | 把策略退化成开关，正常运维降级全部被挡；也无法区分 A 类与 F 类 |
| 降级前统一 `TRUNCATE`/清场 | 破坏数据，且把不可逆变更伪装成可逆 |
| 只在测试里加 `skipif` | 生产仍然会撞上，问题被推迟而不是解决 |
| 依赖 `VALIDATE` 失败兜底 | 破坏性 DDL 已执行，失败时可能已丢列/丢数据 |
| 让迁移自动修复数据 | 迁移静默改写业务数据，审计无法追溯 |

## 附录 A：身份生命周期、迁移授权边界与双向可逆性验收（2026-11-27 技术审查意见）

状态：**DECIDED（项目所有者 2026-11-28 签署 D4-9；独立签署记录见 `docs/adr/ADR-R46-VERSION.txt` VER-0001）**。
本附录与正文一并构成 ADR-R46 的裁决内容；A.2.2 为 Owner 逐字给出的规范文本。

### A.1 身份事实源

1. `role_specs.py` 是角色定义、生命周期、退役状态及其关联约束的唯一事实源。
2. `RETIRED_ROLES` 保留在 `role_specs.py` 内，不建立第二套身份事实源。
3. `identity_registry` 是校验与投影机制，不得反向成为定义源。
4. Bootstrap 负责角色创建、属性设置与生命周期管理。
5. Bootstrap 不得隐式创建或复活已退役角色。

### A.2 Migration 职责边界

**A.2.1 职责归属总表**（Owner 裁决 2026-11-28，D4-9）

| 职责 | 唯一责任方 |
|---|---|
| 基础角色创建 | Bootstrap Identity |
| 角色属性及登录属性 | Bootstrap Identity |
| 密码和可信凭据 | Bootstrap Identity / 可信凭据系统 |
| 角色生命周期（含退役） | `role_specs.py` 及受控身份治理流程 |
| Migration upgrade | 检查角色存在，管理本迁移对象和授权 |
| Migration downgrade | 撤销本迁移创建的授权和对象，不删除基础角色 |

**A.2.2 基础角色与数据库迁移的职责边界**

基础数据库角色的创建、属性管理、凭据配置和生命周期管理属于统一身份治理职责，不属于 Alembic migration 的职责。

Bootstrap Identity 是基础角色创建和属性配置的唯一执行入口，角色属性与生命周期声明以 `role_specs.py` 为准。

新增及整改后的 migration 不得创建、修改或删除基础角色。需要使用基础角色时，必须通过角色存在性断言（`packages.shared.migration_identity.assert_role_present`，缺失时错误信息指向 `scripts/bootstrap_identity.py --roles`）；角色缺失时 fail-closed，不得由迁移隐式创建身份。

Migration upgrade 仅管理本迁移所属的数据库对象及授权；downgrade 仅回收本迁移创建的对象和授权，不得删除基础角色或恢复不属于本迁移的权限。

历史已发布 migration 中的角色创建、属性修改及退役行为属于历史事实。对其进行规范化整改时，必须逐 revision 验证新旧数据库路径兼容性、对象所有权、授权和身份生命周期语义，不得以机械替换代替证据。

退役角色必须登记于统一身份生命周期声明，并通过独立、受控的身份治理流程执行退役。普通 Bootstrap 不得自动恢复退役角色。

所有角色生命周期操作必须保留执行主体、目标角色、影响范围、前置检查、执行结果和审计记录。

**A.2.3 退役不属于迁移的常规职责**（f2b3 裁决：选 A、否决 B）

`f2b3c4d5e6a7` 曾在 `upgrade()` 内执行集群级 `DROP ROLE`，`downgrade()` 内重建该身份。Owner 2026-11-28 裁决：把退役生命周期整体移出 Alembic migration（选项 A），否决「保留迁移内 `DROP ROLE` 并签署单向安全契约」（选项 B）。否决 B 的理由是 B 的前置条件——`cluster_wide_zero_authorization_verified = true`——当前不成立，且不能把「本库 `pg_shdepend = 0`」「某次授权清理成功」或「删除数据库后的局部结果」扩大解释为集群级安全证明。

选项 A 的边界不是「删掉 `DROP ROLE` 就结束」，而是职责整体迁出：

```
Alembic migration          Identity Lifecycle
├── 不执行 DROP ROLE       ├── 读取 RETIRED_ROLES
├── 不在 downgrade 中      ├── 检查集群级依赖（pg_shdepend）
│   CREATE ROLE            ├── 检查角色成员关系
└── 不负责角色生命周期      ├── 检查对象所有权
                           ├── 检查默认权限及授权
                           ├── 执行受控退役
                           └── 输出审计结果
```

该例外不得被引用为其他迁移的先例。

**A.2.4 逐 revision 核验要求**（不批准机械替换后直接交付）

对历史迁移的角色行为做 strip 整改时，每个 revision 必须分别核验：

1. 该角色是否确实属于基础角色，而非迁移专属的临时身份；
2. 是否存在对象所有权、默认权限、成员关系等隐藏依赖；
3. 所有新建数据库路径是否保证 Bootstrap 先于 Alembic；
4. 已有数据库升级路径是否不受影响；
5. `downgrade` / `upgrade` 往返是否不再产生身份面差异。

凡实测出现残留角色（如本轮 `e6a7b8c9d0e1` 的 `qc_worker`）的 revision，必须作为重点回归用例，不能仅凭源码替换宣布修复。

**A.2.5** 不得通过宽泛授权恢复父态权限；downgrade 必须按父态实际权限逐对象、逐角色恢复。

**A.2.6** 无法证明归属或安全性的授权操作必须 fail-closed。

**A.2.7** 不得把其他数据库的授权或依赖误判为当前数据库可清理对象。

**A.2.8** `f2b3c4d5e6a7` 历史上的 `pg_shdepend` 检查只证明该迁移检查过角色依赖，**不证明**所有生产集群都不存在该角色依赖；不得扩大其证明范围，也不得据此把退役当作「已执行」。

### A.3 身份生命周期与退役身份恢复

**A.3.1** 退役角色不得由正常 Bootstrap 自动创建或复活。

**A.3.2 退役的执行载体**：退役由独立、受控的身份治理流程执行（`scripts/retire_legacy_roles.py --retired`，目标清单直接读 `role_specs.RETIRED_ROLES`，不另存注册表）。执行前必须依次检查：集群级依赖（`pg_shdepend` 为权威判据）、角色成员关系（两个方向）、对象所有权（表/schema）、默认权限与显式授权（表/schema/函数 ACL、`pg_default_acl`）。任何一类非空即拒绝执行，工具不代做授权清理。

**A.3.3** 必须区分两个状态，不得混为一谈：

- **`RETIRED`**：身份已登记退役——`RETIRED_ROLES` 中有它，普通 Bootstrap 不再创建它。**不代表**集群里已经删掉了它。
- **`RETIREMENT_EXECUTED`**：真实集群中的退役操作已执行并通过验证——角色已不存在，且执行时前置检查为「全集群零引用」。

**A.3.4** 没有证明可安全删除时**不得强制** `DROP ROLE`。必要时保留身份并限制登录，等待依赖处置；不得为了矩阵转绿牺牲数据所有权与授权安全。现有环境中的 `qc_worker` 必须先完成依赖清查与退役策略裁决。

**A.3.5 恢复的边界与审计痕迹**

1. 若发生受控恢复，必须使用可信凭据来源，并保留历史定义（`historical_attributes`），不得生成声明集之外的身份。
2. 缺少凭据或显式授权时必须拒绝并回滚（`AUTHORIZE_RETIRED_ROLE_RESTORE=<revision>`）；恢复不是降级路径的一部分。
3. 恢复行为的审计痕迹当前仅为同事务内 `RAISE WARNING`（服务器日志级），**不是**持久化应用审计记录；服务器日志是否被集中采集、长期保留、具备不可抵赖性**尚未证明**。
4. `CREATE ROLE` 是**集群级**副作用：在隔离库里降级后角色仍留在集群。本轮实测即因此触发 Registry 漂移（`qc_worker` 存在于集群 → `clean=false`），须由操作者在证据采集后显式清理并复跑 Registry。该副作用必须写入操作手册。

## 附录 C：§8 三项裁决与落地（2026-11-28，VER-0002 追加）

状态：**DECIDED（项目所有者 2026-11-28）**。本附录与正文、附录 A/B 并列；不溯及 VER-0001 的范围声明，

### C.1 裁决一：清单签字人 —— 双签，DBA 为最终签认人

**裁决**：迁移清单采**双签制**。

| 签署方 | 签什么 | 不签什么 |
|---|---|---|
| 迁移作者（revision 实现者） | 「实现与实测一致」：strip/守卫/断言与 checklist 逐条对应，往返证据可复现 | 不代替 DBA 判断目标环境可执行性 |
| 数据库负责人（DBA） | 「目标环境可执行/可回滚」：角色齐备、备份有效、回滚路径可走 | 不代替作者判断实现正确性 |

规则：
1. 缺任一签，清单**不得**视为通过；两签须落在同一 checklist 版本上（版本号+指纹）。
2. DBA 为**最终签认人**：有否决权，无「先上线后补签」。
3. 双签不等于变更授权；正式变更仍走 A.6.6。

**理由**：单一签字会把两类不同风险（代码正确性 vs 环境安全性）压到一个人身上，出问题无法归责；
双签把「谁判断什么」写死，且与 A.6.6 的「执行主体 + 复核」结构一致。

**落地**：`docs/audits/2026-11-28-wp04-strip-checklist.md` 增加双签栏（作者/ DBA + 日期 + checklist 指纹）。

### C.2 裁决二：`guarded` 与 `manual` 的 CI 区分 —— 加一致性断言

**裁决**：

1. `guarded`（自动检查、可自动降级）：**必须**进 CI 往返矩阵（P→U→D 真实往返 + 矩阵条目）。
2. `manual`（需人工确认）：只做「**拒绝自动降级**」断言 + 结构断言（守卫存在、错误可检索、无自动降级分支），
   **不得**被计入往返矩阵的「已证明可逆」；须配套书面人工确认步骤与回执模板。
3. `unsupported`：必须 **fail-closed**——任何自动 downgrade 调用直接拒绝，不得「尽力尝试」。
4. **新增一致性断言**：同一 revision 若声明 `guarded` 却无矩阵条目，CI 必须报错；反之矩阵条目不得引用
   声明为 `manual`/`unsupported` 的 revision。禁止「声明与证据两张皮」。

**理由**：原建议只说了「谁进矩阵」，没说「声明与矩阵不一致怎么办」——那正是分类漂移的入口。
一致性断言把「分类」与「证据」绑死，使矩阵无法靠改文档转绿。

**落地**：`data/migrations/downgrade_modes.json`（`manual` / `unsupported` 显式登记，未登记即默认 `guarded`） + `tests/unit/test_downgrade_modes.py` 四项断言：两集合不相交、登记项必在迁移链上、登记项不得与「已证明往返」冲突（冲突时以证据为准并降级声明）、声明文件键集封闭。
当前 `manual` / `unsupported` 均为空集——断言对空集成立，一旦登记即生效；这不是「没有断言」，而是「断言现在就能拦住第一次漂移」。

   不按谓词删除——按谓词删会在校验与删除之间把新写入的同形行一并删掉而这行**从未归档**；
   删除行数取数据库回执（`RETURNING`）并与归档行数逐项比对；
6. **留证**：归档 CSV + SHA-256 + 行数写入变更记录；备份保留至下一次成功升级后不少于 30 天。

### D.3 明确禁止

1. 按 `sha256` 批量派生定位符（语法合规但内容不存在，等于把脏数据洗成绿灯）；
2. 未完成等值归档即禁用触发器、或先删后补归档；
3. 对可转换行做任何删除；
4. 在已升级到 `d0e1` 之后再用本流程（那时列已是 `varchar` 受控定位符，jsonb 判据不再
   适用；脚本会以显式 ABORT 拒绝，而不是抛一句 `operator does not exist`）；
5. 用 R1 代替「内容真实存在、只是格式旧」的重算路径（那是方案 a，不是 R1）。

# ADR-R39：镜头级引用绑定、引用完整性与约束下沉（再次审查整改）

- 状态：已采纳
- 日期：2026-11-17
- 关联：`代码审查报告-2026-11-17-再次审查.md`（P1-1、P2-3、P2-5、P2-6、P2-7、P3-1、P3-3、P3-4）
- 关联 ADR：ADR-R20（不变量下沉 / 状态机守卫）、ADR-R28（跨域只读经所有者）、
  ADR-R33（产出与资产联动）、ADR-R35（单一路线生成）、ADR-R36（QC 复查会话）
- 契约变更：**无**（本次只改运行时行为与数据库约束；`route_type` 词表问题另见 §3 债务 1）
- 迁移：`a9f1c2e3d4b5`（外键）、`c4e5f6a7b8d9`（证据约束 / 追加式约束 / TRUNCATE 守卫）

## 1. 背景：五个"只差一个维度"的漏洞

再次审查在 `e1f760e` 快照上提出的问题，按"缺了哪个维度"可以归成一组：

1. 跨域归属**只到项目、不到镜头**（P1-1）：`RefOwnership` 只有 `project_id`，
   于是"镜头 A 的规格用在镜头 B"完全合法；选路甚至可以为不存在的镜头登记
   生效路线；
2. 生效路线**只到应用层、不到数据库**（P2-3）：`route_id` 无外键，幽灵引用可
   落库，而这张表不可 UPDATE/DELETE——写错就永久错；
3. 证据要求**只在领域层、不在数据库**（P2-5）：运维播种直连 SQL 可造出"无
   证据的已验证路线"，而选路只认 VERIFIED；
4. 结论追加**只在领域层、不在数据库**（P2-7）：`decisions` 是可变列，直连 SQL
   可整体改写或截断 Gate 追溯所依赖的历史；
5. 重试**只有计数器、没有上限**（P2-6）：失败任务可无限链式重放，每次都是真
   实生成成本。

五条的共同点是「正确性依赖"大家都走服务层"这个假设」。这个假设在运维脚本、
数据修复、未来批量导入面前不成立；而这五条一旦被绕过，产生的都是**无法事后
修正的证据型数据**（生效路线不可改、结论是追溯依据、路线能力目录是选路依据）。
所以整改方向统一为：**能下沉到数据库的不变量就下沉，不能下沉的必须显式传递
维度**。

## 2. 决策

### 2.1 `RefOwnership` 增加镜头绑定维度（P1-1）

`RefOwnership.shot_ids: frozenset[str] | None`：
- `None` = 该类型不做镜头级绑定（如 `DeliveryManifest`）；
- 集合 = 该引用只能用于集合内的镜头（`ShotSpec` / `ShotVisualPlan` 单元素，
  `ConstraintPack` 多元素）。

为什么用"集合 + None"而不是 `shot_id: str | None`：`ConstraintPack` 天然绑定
多镜头（7.9 的 `shot_ids` 是必填数组）。两个字段（`shot_id` / `shot_ids`）会让
每个消费方都要判断"该看哪个"，而一个集合 + None 只有一种读法。

为什么是 `None` 而不是空集：空集在语义上是"绑定到零个镜头"——那意味着"任何
镜头都不许用"，与"没有这条规则"是相反的事实。这与 `eligible: bool | None` 的
既有约定一致（`None` = 没有规则可判，不是默认放行）。

生成侧校验（`GenerationService._assert_ref_owned`）分三条独立拒绝路径，文案
刻意不同：

| 情形 | 错误码 | 为什么分开 |
| --- | --- | --- |
| 对象不存在 | 404 `NOT_FOUND` | 该建对象 |
| 项目不符 | 422 `VALIDATION_ERROR`（ACT-GEN-NEG-001） | 权限越界，该换项目 |
| 项目同、镜头不同 | 422 `VALIDATION_ERROR`（新文案） | **用错了对象**，该换引用或改 shot_id |

三合一会让调用方永远不知道该修什么。跨镜头分支的 `context` 直接给出
`bound_shot_ids`，调用方无需再查一次。

### 2.2 选路要求镜头真实存在（P1-1 下半）

新增端口 `ShotOwnershipPort`（本域定义、组合根实现），只回答两个事实：
`shot_id` 是否存在、属于哪个项目。实现用 `shot_revisions.get_active_by_shot`
（正式镜头修订），**不用 `shot_drafts`**：草案是 AI 拆镜的中间产物，拿它证明
"镜头存在"会让选路落在一个从未被确认的镜头上。

错误码顺序：镜头不存在 → 404；镜头属于别的项目 → 422；然后才查路线。镜头
校验排在路线查找**之前**是刻意的——一个"既没有镜头也没有路线"的请求，报
"镜头不存在"才是准确原因；先报路线会让调用方去建路线，然后再撞一次墙。

### 2.3 生效路线外键（P2-3）

`shot_route_selections.route_id` → `production_routes.entity_id`，`ON DELETE
RESTRICT`（路线本就不可物理删除，这里把"不可删"从权限层再钉一层）。

迁移**先做孤儿行预检**，有孤儿就明确失败并给处置提示，不用 `NOT VALID` 蒙过去：
`NOT VALID` 会把"约束不存在"伪装成"约束存在"，下一个人以为有保护。

> 处置记录（诚实登记）：本仓库开发库里存在 **19 行**历史孤儿（全部 `route_id
> = 'route_first'`，来自旧用例 `test_unique_constraint_rejects_second_row_without_service`
> 用不存在路线直插）。这 19 行本身就是审查结论的实证。清理在维护窗口内进行
> （临时禁用守卫触发器 → 删除孤儿 → 恢复触发器），并同步修正了该用例：现在
> 它先播种真实路线，撞到的是唯一约束而不是外键——否则它测的就不是自己要测的
> 东西。

### 2.4 VERIFIED 必须有证据（P2-5）

`CHECK (status <> 'VERIFIED' OR jsonb_array_length(capability_refs) > 0)`
（约束名 `ck_generation_route_verified_requires_evidence`）。

`verified_by` **没有**一并约束，原因是它目前是**死列**：全仓无任何代码写入它
（`grep verified_by` 只命中 ORM 定义与文档），因为 `UNVERIFIED → VERIFIED` 的
标定入口不是动作矩阵里的 action，只能靠运维播种直插。给一个从未被赋值的列加
`NOT NULL` 只会让播种全部失败，不会提高一点真实性。这条作为新发现登记在 §3。

### 2.5 结论只追加、复核人只增（P2-7）

守卫函数升级为前缀超集校验：

- `decisions`：新数组长度 ≥ 旧数组长度，且**逐项相等**（`0..old_len-1`）；
- `reviewers`：`NEW.reviewers @> OLD.reviewers`（集合只增不减）。

为什么必须逐项比而不是只看长度：整体改写保持长度不变，只比长度等于没检查。
为什么允许追加：改判的唯一合法形态就是"再追加一条"——禁止追加会让"改判"这个
真实业务动作无处安放，最后一定被绕过。

`decisions` / `reviewers` 仍然是"可变列"（否则状态推进也写不进去），限制从
"列级白名单"升级为"列内结构约束"。

### 2.6 TRUNCATE 守卫（P3-1）

行级 `BEFORE UPDATE OR DELETE` 触发器拦不住 `TRUNCATE`（语句级操作，不逐行
触发）。给 `shot_route_selections` 与 `qc_review_sessions` 各加一个
`BEFORE TRUNCATE ... FOR EACH STATEMENT` 触发器。

应用角色本就没有 TRUNCATE 权限，但迁移角色/超户有——"权限挡住了"和"结构
不允许"是两种结论，后者对所有人生效。取证时也必须用超级用户连接验证
（`test_truncate_is_blocked_by_statement_trigger` 就是这么写的）。

### 2.7 重试上限（P2-6）

`MAX_GENERATION_ATTEMPT = 3`，在**受理入口**拒绝（不是 worker 里的"碰运气"
限制——拒绝必须发生在花钱之前）。

基线 9.4 只写"有上限"、没给数字，所以这是**策略常量**而非契约字段（`attempt`
在 schema 里只是计数器）。取 3 的理由：重试通常对应"换参数/换模型"，第三次
仍失败基本说明不是偶发问题；而更长的链会让失败任务变成"总会成功"的无限
重放通道。

### 2.8 ADR 目录按字节保真（P3-3）

`.gitattributes` 增加 `docs/adr/** -text`。理由与 `contracts/**` 相同：
`adr_index.yaml` 是冻结产物⑩，Windows 全新克隆（`core.autocrlf=true`）会把它
检成 CRLF，`freeze_manifest` 的⑩哈希随平台随机报红——偶发失败最终会被当成
噪声忽略，闸门随之失效。

### 2.9 会话与项目绑定（P3-4）

`QCReviewService.decide` 增加 `project_id` 参数并比对 `session.project_id`，
不一致 → 422。授权层按请求体判定，服务层负责"授权对象 = 实际操作资源"。

## 3. 诚实登记的债务

1. **`route_type` 双词表未合流**（审查 P2-4，本轮**未改**）：schema 里是自由
   字符串，代码里是 `ROUTE_TYPES = {blender_scripted, threejs, game_engine,
   external_dcc}` 硬编码 frozenset；基线 9.2.2 的"首批路线抽象"是
   `ImageToVideoRoute` / `TextToVideoRoute` / `PrevizToVideoRoute` /
   `2DLayoutRoute` / `VirtualProductionRoute`。三者是**三套词汇**。
   本轮不动的原因：合流需要先裁定"`route_type` 到底表达实现形态还是路线抽象"，
   这是一个会改契约枚举的产品决策（登记 → 枚举注册表 → bindings → A11 修订），
   不是代码整改。擅自把 `enum_registry` 填成现有四值，等于把"3D 引擎实现形态"
   固化成语义权威——那会让 Phase 1 的"单一路线生成"永远无法登记 AI 生成路线。
   建议下一步单独走契约修订。
2. **`verified_by` / `verified_at` 是死列**：列存在、无任何写入路径（§2.4）。
   要么给它一个入口（VERIFIED 标定的 action），要么删掉——维持现状只会让人
   以为有验证人记录。
3. **14.2 所有权矩阵正文未列 `ShotRouteSelection`**（审查 P3-2）：那是**冻结
   基线正文**，改它需要 A5 式修订；A9 residual 已解释"沿用同域行"。正文补行
   应随下一次基线修订一起做，不宜为零星一行单独开修订。
4. **无路线播种工具**（审查 P3-5）：运维只能直连 SQL 播种路线——正是这条路径
   让 P2-5 的证据约束变得重要。播种脚本属 Phase 2 运维工具。
5. **按项目/按路线的差异化重试上限未建模**（§2.7）：需要项目级策略配置（预算
   与策略域）。
6. **镜头的"存在"以正式修订为准**（§2.2）：若将来引入镜头归档/删除，`resolve`
   必须区分"不存在"与"已归档"——当前没有删除路径，故不区分。
7. **生成侧不重复校验镜头存在性**：受理要求"路线是该镜头生效路线"，而生效路线
   只能由选路产生，选路已校验镜头存在（§2.2）。这是有意的不重复校验；若将来
   允许运维直插生效路线，这条传递性会断——届时必须在受理侧补一次。
8. **孤儿行清理是一次性人工动作**（§2.3）：没有做成可重复脚本，因为"删除受理
   事实"不该被工具化。再有孤儿，迁移会明确失败并要求人工处置。

## 4. 后果

- 正面：五类"绕过服务层就失真"的数据现在有结构防线；跨镜头错配从"合法但错误"
  变成三条可区分的拒绝；Gate/QC 追溯所依赖的结论历史在数据库层不可改写。
- 负面：选路与生成的错误分支变多（每个分支都有独立文案与 `context`），用例
  需要按真实数据播种（镜头必须先存在）——测试准备成本上升，但这正是"测试
  走真实路径"的代价。
- 迁移风险：外键迁移在有孤儿的环境会**明确失败**（不是静默成功），升级前需要
  维护窗口确认数据。
- 未解决：`route_type` 词表（§3.1）仍是"契约与代码各一套"，是下一步最该做的
  契约修订。

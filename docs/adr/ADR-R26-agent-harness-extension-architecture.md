# ADR-R26：Agent Harness 扩展架构（可替换的编排面，不可替换的权威面）

- 状态：**已决策，未实施（设计冻结，2026-11-19）**
- 关联：ADR-069（开放生态采用签名扩展包与沙箱）、ADR-077（Action Registry 是权限判定唯一来源）、
  ADR-078（Agent 仅创建草案）、ADR-096（外部工具四级能力）、ADR-097（外部执行不改变质量治理）、
  ADR-106（Creator Mode UI 降门槛底层不降级）、ADR-R23（状态迁移事实表）、ADR-R25（授权面 == 动作面）
- 上游依据：`contracts/phases/phase_map.yaml`（Phase 0 冻结 Manifest、Phase 3 开放插件且不得直写权威状态）；
  `contracts/action_registry/action_registry.yaml`（发布动作「Agent/Skill/Plugin 不得代发」）
- 触发的契约演进：**无**。本 ADR 不改动任何冻结文件；`capability_scope` 与两条断言的登记
  留到 Phase 3 立项时按 `contract_amendments.yaml` 走（见 §7）
- 触发本 ADR 的问题：产品诉求「像 DeepSeek Harness 那样，让用户最大程度发挥模型能力」

## 1. 问题的实质：契约只有禁令，没有能力面

用户要的是「最大程度发挥模型能力」；契约给的是「插件不得直接写权威状态」。这两句话之间缺了一层：
**被允许的自由长什么样**。

缺这一层的后果是可预测的二元结局：

- 只保留禁令 → 扩展面被压到零，用户发挥不出来（当前状态：Phase 3 才开放，且只有禁令）；
- 只追求自由 → 红线（资产不可覆盖、质量不可暗降、终态不可复活）同时失效，且失效是静默的。

DeepSeek Harness 的做法提供了一个可移植的正面样本，但**移植的必须是机制，不是结论**。
它的自由不是「谁能写」，而是「**谁都能被替换**」：内核极小，模型适配器、工具注册表、
Agent 循环、会话存储、沙箱、调度、UI 全部是插件，任何一块都能换掉而不打补丁核心。
再叠加两个机制：Preset 决定「这台机器加载哪些能力」，Trajectory 记录每次运行并可
inspect / resume / fork / replay。

这三条里，前两条与我们的红线**不冲突**，第三条**恰恰是平台现在缺的**。

## 2. 根因（三层，缺一层都做不对）

### 2.1 「直接」不可判定，于是禁令无法执行

「插件不得**直接**写权威状态」中的「直接」没有定义。把 Agent 循环换成自己的实现，
再在循环里调用已登记 Action——这算直接还是间接？替换掉准入判定所在的组件，让它总是返回
「允许」——这算不算间接写？没有判据时只能靠人审，而人审不进入 CI。

一个反例足以说明问题：Harness 的 Agent 循环是可替换插件。如果准入判定挂在循环里，
那么「循环可替换」就等于「准入可替换」。此时禁令在字面上仍然成立（没人直接 `UPDATE gate`），
但三红线已经全部失效。

### 2.2 Manifest 冻结了外壳，没有声明能力

`ExternalToolAdapterManifest`、`SkillManifest` 在 Phase 0 已冻结（`frozen_inventory.yaml`），
但这两个对象没有任何字段表达「这个扩展被允许做什么」。于是真正的约束只能写在散文里
（Phase 3 那一行「插件不得直接写权威状态」），而散文不进闸门、不进代码。

对比 ADR-R25 的教训：N-06 的根因不是「有人故意多授权」，而是**授权从来没有被声明过**，
于是权限面由表清单决定。这里是同一个形态——扩展的能力面从未被声明，只能由实现者的自觉决定。

### 2.3 没有轨迹，「质量未暗降」不可验证

平台现有两类运行产物：`audit.status_transitions`（事实）与 `outbox.outbox_events`（事件）。
两者都只记录**已经发生的权威变化**，不记录「模型当时看到了什么、试了哪些工具又放弃、
为什么选了这个方案」。

这不是可观测性欠缺，而是**放开自由度的前置条件缺失**：自由度一旦提高，「这次产出比上次差」
就只能靠人感觉。红线「质量不可暗降」在没有轨迹的系统里无法被验证，只能被声明。

## 3. 决策

### D1 三层扩展边界：可替换性由「是否触碰权威事实」决定

| 层 | 内容 | 可替换性 | 依据 |
| --- | --- | --- | --- |
| 编排面 | 模型适配器、工具注册表、Agent 循环、Preset、子代理、技能、会话与 UI | **完全可替换、可热插拔、用户自建** | 不触碰任何权威事实 |
| 边界面 | 外部工具适配器、签名事件回调、模板 | 受限：只能产出候选与证据、只读同步、触发白名单 DAG | Phase 3 契约；ADR-096 / ADR-097 |
| 权威面 | Gate、Canon、Rights、账本、交付 Manifest | **不可替换**：唯一写入者是已登记的 Action | ADR-077；本 ADR D2 |

关键结论不是「禁止替换循环」，而是**把准入从循环里拿出去**：

> 准入不是循环的属性，是 Action 的属性。只要 `owner_action` 的判定位于聚合根
> 且所有者来自 `action_registry`，换掉循环也换不掉准入。

这一点在本轮 D5 已经结构性落地：四个聚合根的 `transition_to` 现在必须接收 action 并交给
`edge_owned_by` 判定，`advance_status` 把它随后写进事实的那个 `owner_action` 原样传下来。
**因此 D5 不只是代码整备，它是本 ADR 的前置条件**——没有它，「编排面完全可替换」这句话
不成立，因为替换循环就能替换准入。

### D2 不变量改写：从「不得直写」到「每次变化必须有一条 Action 事实」

禁令句改写为可判定句（拟登记为 **AUTHORITY-1**）：

> 权威状态的每一次变化，都必须有一条已登记的 Action 事实；该事实记录的 action
> 必须与实际准入判定使用的 action 是**同一个值**；事实必须可追溯到真实主体与会话轨迹。

为什么这是更强的表述，而不是措辞游戏：

1. **可断言**：前半句可以在数据层验证（每张权威表的每次变更都能关联到 `status_transitions`），
   后半句可以在 AST 层验证（写事实的 action 与传给 `edge_owned_by` 的 action 同源）。
   禁令句两条都做不到。
2. **不留绕过路径**：禁令约束「谁写」，改写后约束「变化必须有据」。插件替换循环、
   自建工具、绕开服务层，都必须留下一条登记过的 Action 事实，否则变化本身不成立。
3. **自由度不降**：插件想影响权威状态，路径是「调用 Action」，而 Action 是**可以新增的**
   （经 `contract_amendments` 登记 + 权限 + 审计 + 事件）。能力面因此可以增长，
   只是每一步增长都留痕。

后半句在本轮已经实现一半：`owner_action` 一个参数两处用途（准入 + 事实）。剩下一半
（事实到轨迹的关联）依赖 D4。

### D3 Preset = Profile 组合，不引入新开关

Harness 的 Preset 是「加载哪些插件」。映射到本平台，不做 `enable_xxx` 式布尔开关，而是
**能力集组合**：复用已有的 `CreatorWorkspace.workspace_mode`（创建后不可变，ADR-110）与
`CREATOR_DEFAULT_POLICY`，把 Preset 定义为「一组 Manifest 引用的有序集合」。

理由与 R4（消除重复机制）一致：开关会成为第二份事实源——「用户开了什么」与「实际加载了什么」
必然漂移；组合是派生的，加载结果由组合算出来，不存在第二个真相。

### D4 Trajectory 是一等运行产物，但**不是事实**

轨迹定义为 append-only 会话记录（系统提示、注入的上下文、推理摘要、工具调用与结果、
子代理调度、人工干预点），支持 inspect / resume / fork / replay。

必须写死的一条边界：

> **轨迹不是事实。** 轨迹不得作为准入依据、不得替代 `audit.status_transitions`、
> 不得用于判定「谁做过什么」。事实仍以事务内的 append-only 表为准。

理由是两者的事务属性不同：事实表与状态变更同事务（R07），轨迹是流式、可截断、可重放的；
用轨迹判定权限，等于把「可丢的日志」当成「不可丢的证据」。这条区分不写死，第一个图省事的
实现就会拿轨迹去回答审计问题。

轨迹的用途只有一个，但足够重要：**让「质量未暗降」从声明变成可验证**。放开自由度之后，
判断「这次比上次差」需要对照两次运行分别看到了什么。

### D5 分期落地

| 阶段 | 内容 | 前置条件 |
| --- | --- | --- |
| Phase 1（当前） | **不实现**。本 ADR 只冻结设计 | Phase 1 主链验收 |
| Phase 2 | 轨迹 MVP（记录 + 回放 + 与事实关联）；L2 元数据同步（只读） | D5 已完成；AUTHORITY-1 前半句有断言 |
| Phase 3 | 插件加载器、签名扩展包、白名单 DAG 触发、L3/L4 回调 | 轨迹可用；`capability_scope` 登记完成 |

**为什么先做轨迹、后做插件**：插件开放后，若无法回放，就无法判定「质量暗降」与
「Agent 自批自用」；而轨迹是纯增益、不触碰权威面、不依赖 Phase 3 的插件契约。
顺序反了，等于先拆安全带再装发动机。

## 4. 不照抄「一切皆插件」的三处代价

Harness 的公开实测提供了三条已知代价。照抄会得到「一切皆可绕」，必须逐条处置：

| 代价 | Harness 的表现 | 本平台的处置 |
| --- | --- | --- |
| 脚手架 token | 一次「回复 PONG」首请求约 13,467 input tokens（默认系统提示 + 工具 schema + 仓库规则 + 技能摘要全量随行） | 工具 schema 按 Preset 最小集注入，不做全量随行；脚手架开销纳入预算账本的 `CREATOR_MODE_COST` 子分类（ADR-108），使其可见而非隐形 |
| 隔离默认值 | 沙箱默认「写限制在工作区，读与网络不受限」 | **方向相反**：本平台读边界由组织维度 RLS 强制（SCOPE-4 / ADR-R24），读与写都必须落在租户 + 组织内。照抄默认值会直接击穿已落地的边界 |
| 体积/依赖 | 一次安装 531 包 / 306 MB | 不作为决策因素；模块化单体的依赖治理由 `architecture_check` R1–R3 约束，不因扩展形态放松 |

## 5. 被这一决策触发的连带约束

**A. 扩展不得持有长时凭据。** 边界面插件只能拿 Task 级 Capability Token（ADR-018 / ADR-040），
令牌的作用域与有效期由被触发的 Action 决定，不由插件声明。插件自己声明「我需要什么权限」
等于让它自批自用。

**B. 「不得代发」适用于插件与 Agent 同等。** `CREATOR.PUBLICATION.*` 已有
「Agent/Skill/Plugin 不得代发」（`action_registry.yaml`）。本 ADR 将其上升为一般规则：
任何扩展都不得替用户完成需要用户显式意图的动作；扩展只能准备好候选与证据，最后一跳必须由
用户主体的凭据完成。

**C. 白名单 DAG 是唯一的「间接写入」通道，且它不是写。** L3/L4 回调只能触发白名单 DAG，
DAG 内的每一步仍是已登记的 Action。这条通道之所以安全，不是因为 DAG 可信，而是因为
DAG 内部没有绕过 Action 的路径——与 D1 的结论同源。

## 6. 与既有契约的对应关系（不新增，只映射）

| 本 ADR 概念 | 既有契约落点 | 状态 |
| --- | --- | --- |
| 编排面可替换 | `phase_map.yaml` Phase 0「Agent/Plugin/Adapter Manifest、签名/沙箱/权限契约」 | 已冻结，未实现 |
| 边界面受限 | Phase 3「插件不得直接写权威状态」「L3/L4 只能触发白名单 DAG」 | 已冻结 |
| 不得代发 | `action_registry.yaml` 发布动作的 `approval_requirement` | 已冻结 |
| Creator 隔离 | ADR-106 / ADR-107（CREATOR_GATE 与工业 Gate 独立） | 已冻结 |
| 准入不可替换 | ADR-077 + 本轮 D5（`owner_action` 真准入） | **已实现** |
| 轨迹 | 无 | **缺失**（本 ADR 的实质增量） |

结论：契约**不缺限制，缺的是正面能力面与可复现性**。所以本 ADR 的增量只有两处——
`capability_scope` 声明与 Trajectory，其余是把已有条款串成一条可执行的边界。

## 7. 待登记的契约演进（Phase 3 立项时执行，本 ADR 不改冻结文件）

### 7.1 `SkillManifest` / `ExternalToolAdapterManifest` 增加 `capability_scope`

```yaml
capability_scope: CANDIDATE_ONLY | READ_ONLY | DAG_TRIGGER
```

- `CANDIDATE_ONLY`：只能产出草案/候选与证据（Agent 与绝大多数技能）；
- `READ_ONLY`：只读，含 L2 元数据同步；
- `DAG_TRIGGER`：只能触发白名单 DAG（L3/L4）。

**枚举中刻意没有 `WRITE_AUTHORITY`。** 不是遗漏：权威写入不属于扩展的能力，属于 Action 的
能力。留一个空档比留一个可选项更安全——将来若有人要加，必须改枚举，而改枚举要过
`contract_amendments` 与本 ADR 的复核，不可能顺手加上。

### 7.2 两条断言的设计（本次不实现）

**`authority.action_fact_required`**（4 条判据）：

1. 每张权威表的写路径都能在 `action_registry` 找到对应 action（静态：repository 方法到 action 的映射）；
2. 每次状态变更与 `status_transitions` 事实同事务（静态：同一 UoW 作用域）；
3. 事实中的 `owner_action` 与准入判定使用的 action 同源（AST：同一实参传递，不得二次填写）；
4. 不存在「写入权威表但无 action 上下文」的代码路径（AST + 运行时审计比对）。

**`agent.trajectory_traceable`**（4 条判据）：

1. 每次模型调用产生一条轨迹记录，且记录可关联到会话与主体；
2. 轨迹记录不进入任何准入判定路径（静态：轨迹模块不得被 `authorize` / `edge_owned_by` 引用）；
3. 轨迹可回放：给定记录能重建当时的上下文与工具调用序列；
4. 轨迹与事实可双向追溯：每条事实能定位到产生它的轨迹片段，反之亦然。

**为什么现在不实现**：判据 1–3 需要一个尚不存在的轨迹模块，先写断言只能写成对空表的检查——
那正是「文档销项」的代码版。断言的实现时机与本 ADR 的 D5 分期绑定。

## 8. 残余风险

1. **本 ADR 未实施，冲突面为零但不产生防护**。在 Phase 3 落地前，扩展面仍然只有禁令。
   这是有意的：Phase 1 主链未验收时引入扩展面，会让验收口径失控。
2. **轨迹的存储成本与保留期未定**。Harness 用 zstd JSONL；本平台需与 outbox 保留策略
   （ADR-R06-2 分区）对齐，否则轨迹会成为第二个无界增长的表。
3. **`capability_scope` 是声明，不是执行**。声明本身不阻止越权，必须配 ADR-R25 式的
   最小权限授权（数据库层）与运行期令牌（应用层）。声明的作用是让「越权」有对照物。
4. **Preset 组合的爆炸风险**。能力集组合数会随插件数增长；需要一组经过验证的
   Profile（与 Phase 2「已验证 Profile」的导出契约同源），不允许用户自由拼装到未验证组合后
   再报「工具冲突」。
5. **不覆盖多租户下的插件间通信**。本 ADR 只定义插件与平台权威面的边界，不定义插件之间的
   数据交换；后者需要独立 ADR（涉及租户隔离与数据出境）。

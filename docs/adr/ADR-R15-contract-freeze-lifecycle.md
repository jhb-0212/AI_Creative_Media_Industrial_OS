# ADR-R15：契约冻结生命周期（基线 → 修订 → 派生 → 清单）

- 状态：已采纳（2026-11-16）
- 关联：第三轮深度审查 F1 / F6；基线 §1.3.2 第 1、3 条；§31.11 契约证据清单
- 取代/补充：`contract_check.py` 的职责边界（补 ADR-R07 的豁免规则、ADR-R13 的投递语义之外的契约治理部分）

## 1. 问题（不是「少一个校验」，是生命周期断了）

V2.0.5 冻结时：Action 75 / OpenAPI 75 / Schema 76 / 状态机 35。
到 `7e1c1ad` 实际为 81 / 81 / 79 / 38。

这 6 个 Action、3 个对象、3 个状态机**本身是 Phase 1 主链必需的**（项目→集数→剧本锁定），
问题不在增量，而在于：

1. 派生文件被直接改，没有任何记录说明「谁批的、为什么加、对应哪条基线要求」；
2. 冻结清单（`phase0_manifest.md`）、派生脚本、甚至**基线主文档本身**都没进仓库，
   留在本地 `edit_work/freeze_review/`（该目录现已不存在），冻结包事实上不可复现；
3. 于是 CI 呈现的状态是：`contract_check` 81↔81 自洽 → PASS。**绿得毫无意义**，
   因为它证明的是「两份派生文件互相一致」，而不是「符合 V2.0.5」。

这是「补丁式演进」的典型后果：每次为让功能上线而改派生文件，都像一次无害的小改，
累积起来就失去了与权威源的可追溯关系。按 §1.3.2 第 3 条，这类问题必须在契约层根治。

## 2. 决策

建立**单一**契约生命周期，并把它的每一步都变成仓库内可校验的事实：

```
docs/baseline/AI影视工业化生产平台V2.0.5.md   ← 权威源（随仓库交付，哈希受校验）
                    │
                    │ 只能通过「新修订」改变
                    ▼
contracts/phase0/frozen_inventory.yaml       ← 冻结时刻的名称全集（基线快照）
                    │
        ┌───────────┴────────────┐
        │                        │
        ▼                        ▼
contract_amendments.yaml    派生文件（Schema/Action/State/Permission/OpenAPI…）
（已批准增删及理由）              │
        └───────────┬────────────┘
                    ▼
contracts/phase0/phase0_manifest.md (+ .sha256)   ← 切片证据：字节数 + SHA-256
                    │
                    ▼
scripts/freeze_manifest.py --check                ← 三层判定（唯一实现）
```

判定三层，缺一不可：

| 层 | 判什么 | 为什么这一层不能省 |
|---|---|---|
| 1 权威源 | 基线正文字节数与 SHA-256 | 正文一变就是新修订，旧清单立即失效；不锁这层，「符合 V2.0.5」无从谈起 |
| 2 产物 | 十一类文件字节数与 SHA-256 + 清单自指哈希 | 只锁数量不锁内容，改内容仍能过；只锁内容不锁清单，重签即可洗白 |
| 3 演进 | 实际名称全集 == 基线 ∪ 已批准修订（双向精确） | 只锁数量，可以「删 6 加 6」；只锁哈希，`--write` 一跑就合规 |

第 3 层是核心：它把「合规演进」与「静默漂移」变成机器可区分的两件事，并区分四种失败语义——

- **未登记新增**：绕过了修订流程 → 补登记或回滚，不是改代码；
- **基线项缺失**：冻结内容被静默删除；
- **陈旧登记**：修订还在但实现已没了（台账失真）；
- **同项既加又删**：登记自相矛盾。

`--write` 只负责按实际状态重签清单，**不判断该不该签**。变异验证过：
删掉一个已登记的 Action 再跑 `--write`，第 3 层依然报红。

### 2.1 字节稳定性（否则闸门会随平台漂移）

哈希判定成立的前提是「同一份文件在任何机器上都是同一串字节」。仓库默认
`core.autocrlf=true`（Windows 检出转 CRLF），一旦发生行尾转换，Linux CI 与
Windows 本地算出的 SHA-256 不同——闸门会变成「偶发失败」，而偶发失败最终会被
当成噪声忽略，闸门随之失效。

因此 `.gitattributes` 把 `docs/baseline/*.md` 与 `contracts/**` 标记为 `-text`：
按原始字节存取，不做任何行尾归一化。改这些文件后必须重新 `--write`，
否则 `--check` 报红。这条不是洁癖，是闸门可信度的前提。

## 3. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 在 `contract_check.py` 里加一条「数量必须等于 75」 | 只锁数量：把 6 个合法增量删掉就能变绿，或「删 6 加 6」；且把基线数字硬编码进脚本，下次修订就要改代码。这是补丁，不是根治 |
| 再加一个 `baseline_check.py` 平行校验 | 同一条规则两处维护，必然各自漂移；且不解决「没有权威记录」这个真问题 |
| 直接删掉 6 个 Action / 3 个对象回到 75/75/76 | 会打断已上线的读写接口（PROJECT.READ 等），属于用破坏功能换取数字好看，违反 §1.3.2 第 4 条 |
| 把 `x-afs-p0-coverage.total` 改成 79 了事 | 派生文件自述数量不是权威；改了反而制造第二套「事实」 |
| 把修订记录写在 ADR 里就够了 | ADR 是叙述性文档，机器无法判定「实际集合 == 基线 ∪ 修订」，闸门就退化成人工 review |

## 4. 后果

**收益**

- 「是否符合 V2.0.5」从人工判断变成一条命令，且能区分漂移类型；
- 冻结包可复现：基线正文、清单、修订记录、生成器全部在仓库内，任何人 clone 后可校验；
- 新增契约的流程从「改派生文件」变成「登记理由 → 改派生文件 → 重签清单」，顺序错了会红；
- 补登记的历史被如实标注（`retroactive: true`），不伪装成当时合规。

**代价 / 遗留**

- 每次合法修订要维护 `frozen_inventory.yaml` 与 `contract_amendments.yaml` 两处——这是刻意的：
  前者是「冻结时是什么」，后者是「后来改了什么」，合并成一个文件就无法区分「基线」与「增补」；
- 名称全集判定只覆盖 Action / Schema 对象 / 状态机三类，**未覆盖**字段级变更
  （字段增删仍只能靠 §2 的哈希发现「变了」，不能说明「变了什么」）；
- 本 ADR 只闭合 F1 的机制，**不闭合** F2（数据所有权）、F3（身份与授权）、F4（数据不变量）、
  F5（Phase 1 主链）。那些需要改数据库授权与领域模型，不是契约层能解决的。

## 5. 不做的事

- 不引入外部契约治理工具（Protobuf/Buf、OpenAPI lint）：当前规模下自建 `ast`/YAML 校验足够，
  且能给出中文可读原因；引入工具链要改 `uv.lock` 与 CI 镜像；
- 不做「自动修复漂移」：自动写入 `contract_amendments.yaml` 等于让机器自己批准契约修订，
  直接违反「AI 不绕过审批」；
- 不把基线正文拆成机器可解析的结构：正文是权威叙述，派生是单向的；反向解析正文会引入
  「解析器理解错了正文」这类新风险。

# ADR-R35：镜头生效路线（Phase 1 验收 C4「单一路线生成」的契约载体）

状态：已接受（2026-11-17）
关联：ADR-R33 §3 债务 7（本 ADR 的出处）、ADR-R31/R32（generation_execution 域）、
ADR-R20（状态机下沉数据库）、ADR-028（镜头等级变更与 DAG 最小化 STALE）、
契约修订 V205-R14-A9、Phase 1 验收清单 C4

## 1. 背景与问题

Phase 1 验收清单 C4 的口径是：

> 并发发起两条路线时，首发主链拒绝第二条路线并给出结构化错误，不得静默排队。

ADR-R33 §3 债务 7 已诚实登记：这条要求**没有载体**。具体是三处空洞：

1. `ProductionRoute` 是**平台能力目录条目**（A6 冻结字段集里没有 project/shot
   归属，路线是"平台会做什么"，不是"这个镜头用哪条"）；
2. `PRODUCTION.ROUTE.SELECT` 只往 outbox 写一条 `PRODUCTION_ROUTE_SELECTED`
   事件，**不落任何当前态**——审计事件是事实记录，不是状态存储；
3. 因此：第二条路线照常被接受；同一镜头可以在两个路线上各受理一次生成；
   "这个镜头现在走哪条路线"这个问题，除了翻 outbox 猜最后一次事件之外无法回答。

前两条不是本段引入的缺陷（A6 冻结时就没设计归属），但 C4 的验收不能靠
"查 outbox 里最后一次 ROUTE_SELECTED"来蒙过去：那样做等于把审计表当成状态表，
既制造并发竞争点（两个请求都读到同一事件），又让审计链承担它不该承担的语义。

## 2. 决策

### 2.1 新增载体对象 `ShotRouteSelection`（V205-R14-A9）

字段：`selection_id / project_id / shot_id / route_id` + C.3.1 信封。

**为什么不给 ProductionRoute 加 project/shot 归属**：那会把"能力目录"和
"镜头绑定"两件事塞进同一张表——路线目录由运维/验证工作流播种并按能力演进，
镜头绑定按项目产生；混在一起后，"这条路线属于哪个项目"与"平台支持哪些路线"
互相污染，RLS 与所有权也说不清（目录是租户级平台数据，绑定是项目级业务数据）。

**为什么不复用 outbox 事件**：见 §1 第 3 条。审计事件是 append-only 的事实流，
它回答"谁在什么时候选了什么"，不回答"现在是什么"。用流做唯一性判定，
并发下两个请求都会看到"没有生效路线"。

### 2.2 唯一性由数据库强制，不由应用层"先查后插"

`UNIQUE (tenant_id, project_id, shot_id)`。这是本 ADR 唯一不可替代的结构决策：

- 应用层查重的失败模式是确定的：两个并发请求都在插入前查到"没有"，然后都插入
  成功。加锁可以缓解，但要用什么锁（行锁不存在、advisory lock 需要额外的
  键管理、表锁牺牲并发）都是新的复杂度；
- 唯一约束把"单一路线"变成**不可能被违反的结构事实**，而服务层只负责把
  违反翻译成结构化结论。C4 要的正是"第二条必然失败"，而不是"第二条通常失败"。

仓储层 `add()` 用 SAVEPOINT 包裹插入：唯一冲突会让事务进入 aborted 状态，
没有 SAVEPOINT 的话，冲突后"回查既有生效路线"会拿到 25P02（事务已中止），
本该是"拒绝第二条"，实际会变成"数据库好像坏了"。

### 2.3 三种情形与并发裁决

| 情形 | 结果 |
| --- | --- |
| 该镜头尚无生效路线 | 登记 + 发 `PRODUCTION_ROUTE_SELECTED`，`created=True` |
| 已有生效路线，且与本次选择的路线**相同** | 幂等返回既有记录，`created=False`，**不发事件** |
| 已有生效路线，但**不同** | 409 `ROUTE_ALREADY_SELECTED`，`details` 带 `effective_route_id` / `effective_selection_id` / `requested_route_id` |
| 两个请求并发、路线不同 | 唯一约束裁决：一个成功，另一个落到上一行 |

幂等重放不发事件是刻意的：重复提交不该产生第二条审计事实（D3 要求
"不产生第二条流水"）。事件条数因此可以作为 C4 的结构性证据——并发用例里
"一条生效路线 + 一条事件"才成立。

### 2.4 拒绝，而不是"自动改路"

基线确实提到"路线切换"（第 106/2215 行，白模/控制信号解耦语境），但**动作
矩阵里没有任何 action 表达它**。自动改路会顺手绕过三件必须显式决定的事：

1. **STALE 传播**：换路线意味着已产出的资产可能不再有效（ADR-028 的失效传播），
   这是要按依赖图算的，不是一次 UPDATE；
2. **审批与授权**：谁有权换？换的理由要不要留证？"制片随手点了一下"与
   "导演决定换路线"在审计上必须能区分；
3. **历史处置**：旧的选择记录是改写、作废还是并存？在没有治理语义之前，
   任何选择都会污染"这个镜头走过哪条路线"的回答。

所以在契约补齐这三件事之前，选路入口对"不同路线"一律拒绝——**fail-closed，
而不是 fail-silent**。这也是契约把状态集定为单值 ACTIVE 的原因：造一个
`SUPERSEDED` 却没有任何合法入口，等于在契约里留一个不可达状态。

### 2.5 受理侧也要强制（否则 C4 只守了一半）

`GENERATION.REQUEST` 增加一条准入：**路线必须是该（项目，镜头）当前生效路线**。
未选路或路线不一致 → 409 `ROUTE_NOT_EFFECTIVE`。

只守选路入口是不够的：选路被拒只说明"屏幕上那条没选上"，而请求体里的
`route_id` 仍然可以把生成引到另一条路线上——ADR-R33 债务 7 后半句
"同一镜头也可以在两个路线上各受理一次生成"说的就是这条。

两种不成立的情形都给同一个结论，但拒绝理由不同：

- **未选路**：拒绝而不是"顺手帮你选"。默认选路会让"谁定的路线"这个事实消失，
  出了问题无人可问；
- **路线不一致**：拒绝而不是"按生效路线执行"。静默替换输入，调用方会以为
  自己在跑路线 B，产出的却是路线 A 的东西——这比报错危险得多。

校验顺序刻意排在最末（存在 → 状态 → 引用归属 → 生效路线）：先判请求本身
是否合法，再判状态一致性。请求还没修好时告诉调用方"路线不是生效路线"，
只会把真正的输入错误藏起来。

### 2.6 不可改写：权限 + 触发器双闸

- **权限层**：域角色只有 `SELECT, INSERT`，没有 `UPDATE` / `DELETE`；
- **触发器层**：守卫函数对 `UPDATE` / `DELETE` 一律 `RAISE EXCEPTION`。
  它不是"白名单为空的可变列校验"，而是直接拒绝——比逐列比对更难写错。

只做权限层不够：任何一次误授 `UPDATE` 都会让"不可改写"悄悄失效，而所有测试
仍然绿。所以集成测试两道闸分别验证（应用角色 → permission denied；迁移角色
→ 触发器拒绝）。

### 2.7 审计事件仍归 `ProductionRoute` 聚合

动作矩阵把 `PRODUCTION.ROUTE.SELECT` 的资源类型定为 `ProductionRoute`，
事件目录的 `aggregate_type` 也是 `ProductionRoute`。审计事件的聚合归属不改，
只在 `payload` 里增 `selection_id`（新增事实，不改归属）——事件说"某条路线被
某人在某镜头选定了"，生效路线 id 是这次选择的产物标识。

## 3. 诚实登记的债务（不允许伪装通过）

1. **路线变更没有治理入口**（§2.4）：同一镜头的路线一旦登记，**无法通过平台
   纠正误选**。纠正只能由运维以迁移角色临时停用守卫、改完再恢复（须走变更单
   并留人工记录）。这是刻意的 fail-closed 代价：宁可"改不了、必须有人负责"，
   也不要"悄悄改了、没人知道"。解除条件：调度治理域落地路线变更动作时，同时
   决定 STALE 传播、审批与历史记录处置，并把状态集扩为 ACTIVE→SUPERSEDED。
2. **预算/配额数值校验仍缺位**（R32 债务 1 不变）、**真实供应商适配仍缺位**
   （R32 债务 2 不变）。
3. **R33 债务 1—6 不变**：交付清单止于 DRAFT（联合审批未实现）、PictureLock /
   RightsManifest 未建模、生成准入的状态规则只覆盖契约明写的一项、
   `rights_manifest_ref` 仍是实现扩展列。
4. **C5 / A3 仍无证据**：C5 的 QCIssue 缺陷闭环（`RESOLVED→CLOSED` 跳关拒绝）
   与 A3 的 trace 全链路截图不在本 ADR 范围。
5. **选路的 rights 判定仍依赖下游**：`PRODUCTION.ROUTE.SELECT` 的 rights 准入
   仍由交付域 D3「消费前权利校验」承担（R24 债务），本 ADR 不伪造判定。
6. **生效路线不携带能力匹配证明**：C.4 的 `ROUTE_CAPABILITY_VALIDATE`
   （ShotSpec / 控制信号 / 外观参考 ↔ ModelAdapter.capabilities）仍是 DAG 节点
   语义，未在选路入口校验——当前判定面只有"路线 VERIFIED"。

## 4. 后果

- 正面：C4 从"文档要求"变成**结构事实**（唯一约束 + 双闸 + 受理侧强制）；
  并发第二条路线给出稳定、可编程处理的 409 与结构化 details；
  "这个镜头现在走哪条路线"从"翻 outbox 猜"变成一次主键级查询。
- 代价/风险：选路入口多了一次同域查询（主键级，代价可忽略）；误选无法自助
  纠正（§3 债务 1）；`PRODUCTION.ROUTE.SELECT` 的响应新增
  `selection_id` / `idempotent_replay` 两个字段（向后兼容的增量）。
- 计数变化：schema 对象 85（+1）、状态机 42（+1）、Action 仍为 83（**不开新动作**）；
  新增迁移 1 个（`e1f2a3b4c5d6`）、仓储实现 1 个、端口 1 个、测试文件 3 个
  （领域 / 三副本一致性 / 集成与并发）。
- 对 Phase 1 验收的贡献：C4 由"无证据"转为**有证据**——证据为
  `tests/integration/test_generation_route_api.py`（并发 gather 用例：恰好一个
  200、一个 409，库里一条记录一条事件；另有唯一约束的直连 SQL 用例）与
  `tests/integration/test_main_chain_e2e.py`（主链内联的选路面 + 受理面两条负向
  断言）。

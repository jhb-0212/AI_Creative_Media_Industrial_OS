# ADR-R30: 矩阵概念事件债务台账

日期: 2026-11-17
状态: 已采纳
关联: ADR-R27 §8（ShotChanged 归属核对）、决策 12（事件目录双向校验）、
`contracts/runtime/event_emission_gaps.yaml`（action 级事件缺口台账）

## 背景与问题

基线第 14.2 节所有权矩阵的「主要对外契约」列描述每个模块的契约面，其中
部分事件**只有名字、没有语义定义**（基线全文仅矩阵一处出现，无触发条件、
无 payload 结构），运行时零代码引用。它们是"契约面上的承诺"，不是"已定义
的运行时事件"。

事件目录（event_catalog.yaml）受双向校验约束：**登记的必须真被发出**。
把概念事件预先登记进目录 = 台账撒谎；把它们彻底忘记 = 契约面承诺蒸发。
两条路都不允许，因此需要一个专门的台账回答："这些事件现在是什么状态、
将来由谁、在什么条件下、以什么路径落地。"

## 决策

### 1. 台账位置与本 ADR

概念事件债务以本 ADR 的下表为**唯一权威台账**：

- 不登记进 event_catalog.yaml（双向校验会正确报红）；
- 不登记进 event_emission_gaps.yaml（该台账的作用域是"已实现 action 的
  audit_event 未发出"，概念事件没有绑定的已实现 action，登记进去就是
  孤儿债务——该文件的校验规则第 4 条本身就会拒绝）；
- 事件真正落地（开始发出）当天，本台账对应条目**删除**，同时在
  event_catalog.yaml 登记——与 event_emission_gaps 的"陈旧债务报红"
  同一纪律：台账只存在未兑现的债务，兑现即离场。

### 2. 台账

| 事件 | 责任域（发布方） | 当前状态 | 触发业务场景（解除条件） | 落地路径 |
|---|---|---|---|---|
| `ShotChanged` | shot_planning（Shot/Planning Domain Service） | 概念事件，零承载 | 镜头内容变更需要**跨模块传播**时（如 Blocking/Previz、资产中枢需要感知镜头修订）。单模块内的变更审计由既有 audit/Outbox 事件覆盖，不构成触发条件 | 由 ShotPlanningService 在镜头内容变更提交后发布；先登记 event_catalog（含 payload_required），再实现发布，同一次修订完成（契约先行） |
| `PrevizVersionCreated` | blocking_service（Blocking Domain Service，当前为 `.gitkeep` 占位） | 概念事件，零承载；**责任域本身未落地** | Blocking & Previz 域落地（PrevizVersion 对象进入契约与迁移）且需要对外宣告版本创建时 | 随 blocking_service 域建设一起：对象契约 → 迁移 → 服务 → 事件登记 → 发布，按既有域落地流水线执行 |

### 3. 台账维护规则

1. 新发现的概念事件（基线矩阵出现但目录未登记且无实现承载的）必须追加
   到本表，写齐五列；
2. 任何"提前登记进 event_catalog"或"无场景就实现发布"的动作都是违反
   双向校验纪律的缺陷，架构闸门/评审应拒绝；
3. 事件落地后删除条目，并在关联域 ADR 中留痕（引用本 ADR）。

## 后果

- 正面：契约面承诺有了唯一、可查询的权威状态；"忘记"与"抢跑"两个失败
  模式都被结构性排除。
- 负面：多一份需要随域建设维护的台账（两行规模，维护成本可忽略）。
- 验证：人工评审核对（台账规模过小、生命周期过长，不值得为其建自动化
  闸门——为两行 YAML 建扫描器违背"一个规则一个权威实现"的节制度）。

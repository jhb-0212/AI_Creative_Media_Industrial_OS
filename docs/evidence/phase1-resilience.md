# Phase 1 韧性证据：并发、崩溃恢复与崩溃重投

被测系统：AI Creative Media Industrial OS V2.0.5（模块化单体 + 异步 Worker）
测量对象：生成主链（GENERATION.REQUEST → worker 执行 → 产出登记为资产版本）
对应契约：9.4（重试与故障分类）、12.6（运行可靠性目标）、
ADR-R34（租约与崩溃接管）

- 机器可读证据：`docs/evidence/phase1-resilience.json`
- 复现命令：`python scripts/resilience_check.py`
- 测试套件：`tests/resilience/`（`pytest -m resilience`）

## 1. 结论

| 能力 | 状态 | 依据 |
| --- | --- | --- |
| 多 worker 并发执行 exactly-once | 通过 | 6 worker × 24 任务：成功 24、资产版本 24、重复 0 |
| 并发受理不丢不串 | 通过 | 20 并发：PENDING 20、GENERATION_REQUESTED 20 |
| Worker 崩溃 → 租约到期重新调度 | 通过 | 6 个崩溃任务 1.21s 内全部接管完成（目标 300s） |
| 幂等重试（重放登记） | 通过 | 同一任务登记 2 次 → 1 个资产版本 |
| Outbox「处理成功、ack 前崩溃」不丢 | 通过 | 投递 2 次、发布 1 次、丢失 0 |
| 已终态任务不复活、不重复执行 | 通过 | 再跑一轮：claim/reclaim/succeeded 全 0 |

**结论范围**：以上证明"行为在并发与崩溃下正确"，不证明生产容量（见 §5）。

## 3. 场景与结果

### 3.1 并发执行 exactly-once（核心不变量）

规模：24 个 PENDING 任务，6 个 worker 并发持续排空，租约 300s。

| 指标 | 值 |
| --- | --- |
| 成功执行 | 24 / 24 |
| 领取成功 | 24（每任务恰好一次） |
| 幂等跳过 | 0 |
| 资产版本 | 24（每任务恰好一个） |
| 吞吐 | 53.6 任务/秒（0.448s 完成 24 个） |

关键断言：`succeeded == task_count` 且 `asset_versions == task_count` 且每个
任务的 `result_ref` 指向**自己的**资产版本。多一个成功就是重复执行，多一个
资产版本就是重复计费。

**改造前后对比**（同机、同规模，测试形态相同）：乐观逐个领取时 6 个 worker
读到同一个"最早 16 条"窗口，产生 **113 次幂等跳过**、吞吐 40.8 任务/秒；
改为 `FOR UPDATE SKIP LOCKED` 批量领取后跳过 **0**、吞吐 **57.4 任务/秒**
（本次快照 53.6，落在抖动区间内）。正确性两版都成立，差别在空转。

### 3.2 并发受理延迟

| 指标 | 值 |
| --- | --- |
| 串行基线 p50 | 26.1 ms |
| 20 并发 p50 / p95 / max | 576 / 601 / 619 ms |
| 受理吞吐 | 32.0 请求/秒 |
| 落库结果 | PENDING 20、GENERATION_REQUESTED 20 |

解读：串行 26ms 说明单请求本身是轻的；20 并发 p95 约 600ms 是**排队**结果
（单进程事件循环 + 每请求 3 次跨域只读解析 + 域角色连接池），不是单请求变慢。
要提升这一项需要多进程/多副本部署与连接池调参——属容量工程，不在本证据范围。

### 3.3 Worker 崩溃恢复

场景：6 个任务被 worker 领走（`RUNNING`，租约 1s）后进程死亡，不写终态、
不续租；另一个 worker 轮询接管。

| 指标 | 值 |
| --- | --- |
| 崩溃任务数 | 6 |
| 被接管（reclaimed） | 6 |
| 恢复耗时 | 1.21 s（目标 ≤ 300 s） |
| 产出资产版本 | 6（幂等重试未产生重复） |
| 恢复后持有者 | 全部转移到存活 worker |

演练租约取 1s（生产默认 300s），所以"1.21s 恢复"证明的是**机制**：
租约到期即可接管，恢复延迟 ≈ 租约剩余 + 一个轮询周期。生产口径下最坏
≈ 300s + 轮询间隔，仍在 12.6 的 5 分钟目标内。

**崩溃是模拟的**：用 SQL 把 `lease_expires_at` 推到过去，不依赖优雅停机钩子。
如果恢复只能由停机钩子触发，它救不了 `kill -9`。

### 3.4 Outbox 崩溃重投

场景：handler 执行成功、ack 提交前进程崩溃（提交阶段抛错）。

| 指标 | 值 |
| --- | --- |
| handler 投递次数 | 2 |
| 去重后事件数 | 1 |
| 最终发布次数 | 1 |
| 丢失 | 0 |

这正是"至少一次"的字面含义：**重复是语义，不是缺陷**；消费方必须按
`event_id` 幂等。已有测试覆盖"handler 抛异常 → 不 ack → 重试"的失败路径，
本用例补的是"成功之后崩溃"这个更窄、也更常被实现忽略的窗口。

## 4. 本段修掉的真实缺口

1. **崩溃任务永久卡死**：段 3 只有 PENDING 扫描，领取后崩溃即停在 RUNNING。
   契约 9.4 / 12.6 / state_machines 注都写了"租约到期重新领取"，但运行时
   没有租约这一事实。现在有：`lease_owner` / `lease_expires_at` + 谓词 CAS
   接管 + 终态栅栏（ADR-R34）。
2. **并发领取空转**：6 worker 抢同一窗口，113 次幂等跳过。改为
   `FOR UPDATE SKIP LOCKED` 批量领取（与 outbox relay 同范式）。
3. **两条状态推进路径**：`GenerationService.claim/succeed/fail` 是无调用方
   的第二套写口，且不校验租约——保留它等于保留绕过栅栏的通道。已删除。
4. **RLS 事务语义陷阱**：`SET LOCAL` 上下文在 commit 后失效，紧随其后的
   过期租约查询会被 RLS 判否并**静默返回空表**——看起来像"没有崩溃任务"。
   已把两个查询放回同一事务，并在代码注释里写明原因。

## 5. 未覆盖 / 未证明（诚实边界）

1. **执行中续租（heartbeat）未实现**：确定性适配器亚秒级，300s 租约不会
   误判；接真实供应商适配时必须续租，否则长调用会被接管并重复提交。
2. **接管不查询上游作业状态**：9.4 要求"先查询 Provider Job"。Phase 1 无
   外部作业可查；真实适配器接管前必须查，否则同一作业提交两次。
3. **RPO/RTO 未演练**：Project DB / 对象存储 / Workflow Runtime 的备份恢复
   需要独立环境与故障注入，本证据只覆盖 Worker 崩溃与 Outbox 崩溃重投。
4. **Outbox 延迟 SLO 未测**：验证了"不丢不重"的语义，P95 ≤ 30s 的延迟目标
   需要持续流量与时间窗口。
5. **规模有限**：24 任务 / 6 worker / 20 并发。证明行为正确与退化趋势，
   不构成容量承诺（12.6 明确要求容量测试后按成本/风险校准）。
6. **未做长稳与资源泄漏观察**：没有连续数小时的连接池/内存曲线，只有
   单轮场景。

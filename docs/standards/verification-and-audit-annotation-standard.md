# 核验与审计标注规范（V1.0）

> 适用仓库：`AI_Creative_Media_Industrial_OS`
> 权威性：本文件是**标注词汇与报告格式的唯一权威**。除本文件外，仓库内不得另立一套核验/审计/整改标注（新增词汇须先改本文件）。
> 定位：本规范**不新增任何工程判定规则**。判什么合规、什么违规，权威仍是基线
> `docs/baseline/AI影视工业化生产平台V2.0.5.md` 与已批准的 ADR；本规范只规定「如何把判断过程与证据写清楚」。
> 与既有闸门的分工：`freeze_manifest` / `contract_check` / `architecture_check` / `merge_readiness` 各自回答一个具体问题，
> 本规范不重复它们的规则，只要求报告**引用它们真实执行的结果**。

---

## 0. 为什么需要两套标注

核验与审计回答两个不同的问题，混用会让结论失去分辨力：

| 体系 | 回答的问题 | 判据来源 |
|---|---|---|
| 核验（Verification） | 这个**事实**是否成立？证据够不够？结论能否复现？ | 可直接观测的证据（文件、代码、命令输出、数据库状态） |
| 审计（Audit） | 这个实现**是否符合基准**？有没有违反铁律、有没有架构风险？该怎么整改？ | V2.0.5 条款、已批准 ADR、已冻结契约 |

两者必须能组合出「事实成立但不合规」这种结论：

> `[V-VERIFIED][E2+E4]` 「ConstraintPack 的三条治理边无运行时入口」这一事实成立；
> `[A-GAP][P2-MEDIUM]` 相对 7.9 的五态四边要求，它仍是实现缺口。

若把两者压成一个 PASS/FAIL，则「确实实现了」与「实现得对」互相掩盖——这正是本规范要防的第一类错误。

**禁止的等价替换**（违反即视为标注造假）：

1. 文档写了 ⇒ 代码实现了；
2. 代码存在 ⇒ 测试跑过了；
3. 测试通过 ⇒ 架构合规 / 生产可用；
4. 提交说明或 PR 描述里的 PASS ⇒ 独立核验通过；
5. 模拟/内存替代实现通过 ⇒ 真实数据库/真实服务通过。

## 1. 核验标注体系（Verification）

### 1.1 核验状态

| 标注 | 名称 | 判定标准 |
|---|---|---|
| `[V-VERIFIED]` | 已核验 | 已取得直接证据，可独立复现并确认结论 |
| `[V-PARTIAL]` | 部分核验 | 部分事实已确认，证据不足以支持完整结论 |
| `[V-UNVERIFIED]` | 未核验 | 尚未取得足够证据，不能判断真实状态 |
| `[V-FAILED]` | 核验失败 | 已执行核验，结果与预期不一致 |
| `[V-BLOCKED]` | 核验阻塞 | 因环境、权限、依赖或外部条件无法完成核验 |
| `[V-NA]` | 不适用 | 该项不属于当前核验范围 |

`[V-BLOCKED]` 与 `[V-FAILED]` 必须区分：前者是「没拿到证据」，后者是「拿到了反向证据」。
把阻塞记成失败会冤枉代码，记成通过则是本规范最严重的违规。

### 1.2 证据等级

| 标注 | 证据类型 | 说明 |
|---|---|---|
| `[E1]` | 文档证据 | ADR、基线、设计文档、决议文件 |
| `[E2]` | 仓库证据 | 实际代码、配置、迁移、契约、脚本、哈希复算 |
| `[E3]` | 静态检查证据 | 类型检查、Lint、静态分析、结构/分层检查 |
| `[E4]` | 自动化测试证据 | 单元、集成、契约、端到端测试的**真实执行记录** |
| `[E5]` | 运行证据 | 真实 PostgreSQL、服务运行、迁移往返、端到端链路 |
| `[E6]` | 独立复核证据 | 独立环境复现、第三方验证、独立审查记录 |

证据使用规则（与 §0 的等价替换一一对应）：

1. 文档声明不能代替代码证据（E1 不升级为 E2）。
2. 代码存在不能代替运行证据（E2 不升级为 E5）。
3. 测试文件存在不能代替测试实际执行（E2 不升级为 E4）。
4. 提交说明中的 PASS 不能直接标记为独立核验通过（他人声明只能是 E1）。
5. 模拟测试不能代替真实数据库测试（E4 不能冒充 E5）。
6. 单次测试通过不能证明生产环境可靠（E4/E5 不覆盖容量与长稳）。
7. 证据必须关联具体提交 SHA、文件路径、行号、命令或运行日志；缺定位的证据不计入等级。

### 1.3 核验结果表达格式

```text
[V-状态][E-等级] 核验对象：结论；证据：具体位置；限制：尚未覆盖的内容。
```

示例：

```text
[V-PARTIAL][E1+E2] Phase 0 冻结：仓库存在冻结清单及基准文件哈希；
证据：contracts/phase0/frozen_inventory.yaml:7-11，freeze_manifest.py --check 退出码 0；
限制：尚未独立复算签署决议原件，冻结清单的「人类批准」环节无可机检证据。
```

`限制：` 字段不得省略、不得写「无」以外的含糊措辞。写「无」表示已穷尽该对象在当前范围内的证据面。

### 1.4 证据时效

标注是**时点判断**，不是长期属性：

- 每条核验标注必须附着被核验对象的提交 SHA（或数据库版本号）；
- 被核验对象的字节内容变更后，原标注自动失效，必须重跑；
- 引用历史报告时必须同时写明其 SHA，禁止用「上次审计说 PASS」代替当前核验。

## 2. 审计标注体系（Audit）

### 2.1 审计结论

| 标注 | 名称 | 判定标准 |
|---|---|---|
| `[A-COMPLIANT]` | 符合基准 | 实现与明确的基准要求一致，且有证据支持 |
| `[A-NONCOMPLIANT]` | 基准违规 | 实现明确违反 V2.0.5 或已批准的 ADR |
| `[A-PARTIAL]` | 部分符合 | 已实现部分要求，尚未形成完整闭环 |
| `[A-GAP]` | 实现缺口 | 基准要求明确存在，代码或运行能力尚未实现 |
| `[A-RISK]` | 架构风险 | 当前未必违反明文要求，但存在可识别的系统性风险 |
| `[A-OPTIMIZE]` | 优化建议 | 不构成明确违规，属质量、效率或可维护性改进 |
| `[A-UNKNOWN]` | 待判定 | 证据不足，无法得出审计结论 |

`[A-UNKNOWN]` 必须同时给出「缺什么证据才能判定」，否则等同于放弃审计。

### 2.2 严重程度

| 标注 | 级别 | 说明 |
|---|---|---|
| `[P0-CRITICAL]` | 致命 | 破坏核心安全、数据完整性、权限边界或关键业务链路 |
| `[P1-HIGH]` | 高 | 违反关键工程约束，可能造成严重业务或架构后果 |
| `[P2-MEDIUM]` | 中 | 存在明显实现缺口或局部架构问题 |
| `[P3-LOW]` | 低 | 局部质量、维护性或效率问题 |
| `[P4-INFO]` | 信息 | 记录性发现，不要求立即整改 |

定级按**实际影响**判断，不按模块重要性。核心模块里的注释错字不是 P0；边缘模块里的越权才是 P0。

### 2.3 工程铁律标注（编号裁定）

每项审计发现必须关联对应铁律。**但铁律编号不由本规范定义**：

- 五条铁律的唯一权威是基线 §1.3.2「工程质量与 AI 辅助开发规则（实现必须强制）」；
- 标注格式为 `[IR-1.3.2-N]`，N 取 1–5，直接对应基线条号；
- 形如「IR-01 单一事实源」「IR-03 根因治理」这类**别名可用于阅读**，但不得作为独立编号体系引用，
  也不得据此认定违规——违规判定必须同时引用基线条文。

| 标注 | 基线条款 | 审查重点 |
|---|---|---|
| `[IR-1.3.2-1]` | §1.3.2-1 架构无屎山 | 模块边界、数据归属、依赖方向、平行重复模块、空壳透传 |
| `[IR-1.3.2-2]` | §1.3.2-2 代码无屎山 | 重复实现、超长函数、职责混乱、绕开领域模型的临时特判 |
| `[IR-1.3.2-3]` | §1.3.2-3 禁止补丁式演进 | 临时绕过、平行表、兼容层叠加、魔法开关 |
| `[IR-1.3.2-4]` | §1.3.2-4 保持高技术标准 | 可运行代码、测试、契约、运行证据的完整交付 |
| `[IR-1.3.2-5]` | §1.3.2-5 全程 AI 辅助、人类负责 | 人类审批、权限隔离、AI 不得越权 |

> 裁定理由（本条不得被后续文档绕过）：README「工程铁律」一节明确规定「本仓库不自定义铁律」，
> 并记录了历史上自造五条铁律导致口径分裂、最终回退的教训（`docs/audits/2026-11-16-review-round3-response.md`）。
> 再造一套 IR-01…05 编号，等于给同一组规则建第二个权威源——这本身就是 §1.3.2-1 的违规。

### 2.4 审计发现格式

每项发现必须包含十个字段，缺一不可：

1. 编号
2. 审计结论
3. 严重程度
4. 对应基准条款
5. 对应工程铁律
6. 实际代码/运行证据（file:line 或命令）
7. 根本原因
8. 影响范围
9. 系统性整改方案
10. 验收标准

标题行格式：

```text
[A-审计结论][P-严重程度][IR-1.3.2-N]
```

「根本原因」不得写成症状复述。`def f()` 里多了个 `if` 是症状，真正的根因通常是
「某个事实没有权威源」「某个边界没有建模」「某条不变量放在了错误的层」。
写不出根因时，结论应降级为 `[A-UNKNOWN]` 并列出待查项，而不是编一个原因。

## 3. 整改状态标注（Remediation）

整改与审计发现**分开管理**：一个问题可以有多个整改项，一个整改项可以修多个问题。

| 标注 | 状态 | 判定标准 |
|---|---|---|
| `[R-OPEN]` | 待整改 | 已确认问题，尚未开始 |
| `[R-PLANNED]` | 已制定方案 | 方案已确定，尚未实施 |
| `[R-IN-PROGRESS]` | 整改中 | 已开始修改 |
| `[R-IMPLEMENTED]` | 已实现 | 代码修改完成，尚未完成验收 |
| `[R-VERIFIED]` | 整改已验证 | 已通过对应核验及验收标准 |
| `[R-REJECTED]` | 整改未通过 | 修改后仍不满足要求 |
| `[R-DEFERRED]` | 延期处理 | 经授权明确延期，并记录原因与风险 |
| `[R-ACCEPTED-RISK]` | 风险接受 | 有权责任人明确接受残余风险 |

三条硬规则：

1. `[R-IMPLEMENTED]` ≠ `[R-VERIFIED]`。代码改了不等于根因消除了。
2. `[R-DEFERRED]` 与 `[R-ACCEPTED-RISK]` 必须写明授权人与到期条件，否则退回 `[R-OPEN]`。
3. 整改状态变更必须能指向一次提交或一份验收记录；无证据的状态变更无效。

## 4. 审计判断原则

### 4.1 依据优先级

1. V2.0.5 正式基准及其**已登记**修订（`contracts/phase0/contract_amendments.yaml`）；
2. 已批准的 ADR；
3. 已冻结的契约与清单；
4. 实际代码、配置、数据库与运行证据；
5. 工程推导与优化建议。

ADR 与基线冲突时，必须判断是否走过正式修订流程，**不得用 ADR 直接覆盖基线**。
同理，本规范与任何报告的措辞冲突时，以基线为准。

### 4.2 四种情况必须分开

| 情况 | 标注 |
|---|---|
| 基准明确要求，但没有实现 | `[A-GAP]` |
| 实现违反基准 | `[A-NONCOMPLIANT]` |
| 基准无明确要求，但存在潜在系统性问题 | `[A-RISK]` |
| 当前符合要求，仍有提升空间 | `[A-OPTIMIZE]` |

最常见的一处误用：把「整体验收证据不足」写成「整个 Phase 都没实现」。
前者是 `[A-GAP]`（证据缺口），后者是 `[A-NONCOMPLIANT]`（实现缺失）。两者的严重程度与处置完全不同。

### 4.3 根因治理的准入条件

整改**不得**只新增一层：

- 新的 Guard / Manager / Policy / Registry / Checker / Factory；
- 新的兼容层、并行数据表、并行命令清单；
- 新的「只让测试变绿」的兜底分支。

必须先确认现有机制的职责与事实源，再选择：合并、删除、替换、迁移、重构。
确需新增机制时，方案里必须回答五个问题：

1. 原机制为什么不能承担这个职责；
2. 新机制的唯一职责是什么（一句话，含「不负责什么」）；
3. 是否存在重复实现（列出被它替代的旧路径）；
4. 是否破坏原有数据归属与依赖方向；
5. 如何移除旧机制，或兼容期限到何时。

回答不出第 3、5 项的新增，一律视为 `[R-OPEN]` 不得进入实施。

### 4.4 验收条件（全满足才是 `[R-VERIFIED]`）

- 根因已消除（不是症状消失）；
- 不存在同类重复机制；
- 对应基准要求已满足；
- 必要测试已**真实执行**（不是「已存在」）；
- 关键运行场景已验证（涉及数据的必须真库）；
- 验收证据可复现（命令 + SHA + 输出）；
- 不存在通过降低标准或绕过检查获得的 PASS。

## 5. 核验总表不得手写

这是本规范相对「人工清单式审计」的唯一结构性改动。

**问题**：手写的核验表（V-001…V-007）是一份快照。它腐烂的方向永远是不安全的一侧——
新增了一类可核验对象，表里不会多一行，于是漏检表现为正常；某项标注过时，没人会回头改。
这与仓库既有的「数量判据 = 手写快照 = 技术债」结论一致。

**做法**：

- 规范只固定**七类核验对象**（下表），不固定具体条目；
- 具体条目由 `scripts/verification_battery.py` 的探针注册表派生，报告正文由脚本生成；
- 脚本自带双向完备性判据：某类对象无探针 → 报红；探针声明了未登记的类别 → 报红；
- 静态/契约类检查一律委托 `scripts/merge_readiness.py::CHECK_COMMANDS`，**不复制命令清单**
  （第二份命令清单必然与第一份漂移）。

| 类别 | 核验对象 | 主要证据等级 |
|---|---|---|
| `C1` | 基准文件完整性（字节数、SHA-256、唯一副本） | E2 |
| `C2` | 冻结清单（`freeze_manifest --check`、修订台账） | E2+E3 |
| `C3` | 契约一致性（`contract_check`、派生文件交叉引用） | E3 |
| `C4` | Manifest 哈希（正文与侧车 `.sha256` 独立复算） | E2 |
| `C5` | 静态与结构检查（ruff、mypy、分层依赖；条目由 `merge_readiness.CHECK_COMMANDS` 派生） | E3 |
| `C6` | 数据库迁移（heads/current 一致、`alembic check` 无漂移） | E5 |
| `C7` | 自动化测试与核心链路（分层执行、端到端主链） | E4+E5 |

> 七类覆盖「代码现状」与「运行现状」，但不覆盖「生产就绪」。容量、长稳、真实第三方模型调用
> 等必须由独立压测与试运行证明，不得由 C1–C7 的任何绿灯推出。

### 6.4 最终结论：九项状态，禁止只给一个 PASS

| 标注 | 含义 |
|---|---|
| `[FREEZE-STATUS]` | 冻结状态 |
| `[CONTRACT-STATUS]` | 契约一致性 |
| `[ARCHITECTURE-STATUS]` | 架构合规性 |
| `[IMPLEMENTATION-STATUS]` | 实现完整性 |
| `[TEST-STATUS]` | 测试可信度 |
| `[RUNTIME-STATUS]` | 运行验证状态 |
| `[SECURITY-STATUS]` | 安全与权限状态 |
| `[REMEDIATION-STATUS]` | 整改闭环状态 |
| `[RELEASE-STATUS]` | 交付与发布状态 |

每项取值：`VERIFIED` / `PARTIAL` / `FAILED` / `BLOCKED` / `UNDETERMINED` / `NA`，
并必须附：支撑它的核验编号、未覆盖面、以及「要升到 VERIFIED 还缺什么证据」。

这九项是**审计判断**，不是机器结论：由报告人工给出，逐项引用 §6.1 的核验编号与核验电池输出的关键指标。
核验电池只产出「事实 + 证据等级」，不得替报告宣称「合规 / 生产可用」——
把判断也自动化，等于让「检查器返回 0」冒充「架构合规」，正是 §0 禁止的第三种替换。
因此九项状态随报告一起按提交 SHA 归档，不维护成一份跨版本持续更新的清单。

最终结论必须逐条回答：

- 哪些已经核验；
- 哪些仅有仓库声明（E1/E2）而无运行证据；
- 哪些完全没有证据；
- 哪些违反基准；
- 哪些存在架构风险；
- 哪些已整改并通过验收；
- 哪些问题阻塞后续阶段。

---

## 7. 执行口径

```text
核验：先证明事实。
审计：再判断合规。
整改：消除根因。
验收：用证据证明整改有效。
```

> 以 V2.0.5 为准绳，以工程铁律为红线，以实际代码为对象，以运行证据为依据，以根因消除为整改目标。

三条永不允许的替换（与 §0 同一组规则，此处为对外口径）：

1. 把文档写了当成代码实现了；
2. 把代码实现了当成测试通过了；
3. 把测试通过了当成架构合规、生产可用。

## 1. 背景与定位

第三轮审查（F09）指出：代码已具备连接池、Redis 限流、Outbox 重试、熔断、
OpenTelemetry、Prometheus 指标等基础设施，但**没有压测与故障演练实测证据**。
`pool_size=10 / max_overflow=20` 只是单进程连接池参数，不代表平台能承受
每秒 1000 次请求。

本方案不声称「压测已通过」，而是把「该测什么、怎么测、什么算通过」落到
可执行产物，使压测从「想起来才做」变成「有标准可依」。

## 2. 压测目标与验收阈值

阈值是**首期基线**，不是最终容量承诺；达到后按业务增长重新标定。

**每个阈值都隐含一个并发前提**，不写清前提的阈值无法判定。探针的 50ms 尤其
如此：它是按「轻量读」设的，而轻量读的实现前提是缓存（见 §2.1）。

| 指标 | 验收阈值（首期） | 并发前提 | 说明 | 2026-11-18 本机实测（次轮） |
|------|-----------------|---------|------|--------------------|
| 探针 GET /readyz | P99 < 50ms | **5** | 编排系统轮询，非持续并发 | P99 24.6ms ✅ |
| 探针 GET /readyz | P99 < 50ms | 20 | 容量压力档，用于观察排队 | P99 303.6ms ❌ |
| 只读 GET /assets/{id} | P99 < 200ms，错误率 < 0.1% | 20 | 验证 RLS 查询 + 鉴权路径 | P99 215.6ms / 0% ❌ |
| 写 POST /assets | P99 < 500ms，错误率 < 1% | 20 | 验证事务 + Outbox + 乐观锁 | P99 368.4ms / 0% ✅ |
| 并发上限 | 无 5xx 雪崩，限流按阈值返回 429 | — | 验证背压，不静默堆积 | 119×201 + 381×429 ✅ |

上表是**单机单进程**数据（压测客户端与 API 同机），只用于登记当前基线，
不作为通过依据；目标环境复测前，判定都不改变。

**为什么探针要分两行**：这不是挑数据。`/readyz` 命中缓存时是纯内存读
（单请求 2ms），20 并发下的 303ms 来自「客户端与 API 争同一颗 CPU」的串行
排队——本机 QPS 随并发增加而下降（433→255），说明瓶颈在客户端侧。
探针的真实负载是编排系统每 5–10 秒一次，5 并发已覆盖上界；
20 并发那一行保留，作为「本机不能标定容量」的证据。

### 2.1 探针阈值的实现前提（本轮已落实）

50ms 的阈值只有在**探针是轻量读**时才有意义。此前 `/readyz` 每请求真探两个域
连接池 + 读 `alembic_version`（三次往返，约 90ms），于是要么放宽阈值、要么改
实现。选择的修法是不动阈值：

- `ReadinessProbe` 提供 TTL 缓存（默认 1s）+ 单飞 + 超时；
- 失败结果同样缓存——故障期探测最贵（要等超时），不缓存会让探针成为压死
  连接池的最后一下；
- 缓存 TTL 与超时由 `READINESS_CACHE_TTL_SECONDS` / `READINESS_TIMEOUT_SECONDS`
  配置，构造期校验（TTL 为负、超时为 0 直接拒绝启动）。

代价是「恢复最多迟 1 秒被发现」——相对于编排系统秒级到十秒级的摘流/恢复传播，
这个取舍是明确的。

**关于 QPS ≥ 500/实例**：本轮把这条从探针行移除了。不是降低标准，而是它在
本机**不可测**——压测客户端与 API 同机时，单线程事件循环的上限是 433 QPS
（并发 1 时已达 433，再加并发反而降到 255）。用一个测不出来的数字当验收线，
只会得到「看起来没达标」或「挑一次达标的数字」，两种都不诚实。
该指标移到阶段 B，前提是**独立压测机**。

## 3. 压测矩阵

按「单实例基线 → 多实例扩展 → 故障注入」三阶段递进：

### 阶段 A：单实例基线
- 目标：确认单进程在 pool_size=10/max_overflow=20 下的真实吞吐。
- 步骤：
  1. `docker compose up -d postgres redis migrate api`（本地/单机编排）；
  2. 跑探针压测（验收口径 5 并发；另跑 20 并发观察排队行为）：
     `python scripts/perf/load_test.py --probe-only --concurrency 5 --requests 300`；
  3. 跑只读压测：`python scripts/perf/load_test.py --path /assets/{id} --token <token>`；
  4. **跑写路径压测**（事务 + Outbox + 乐观锁的唯一证据来源）：
     `python scripts/perf/load_test.py --write-path --project-id <perf-project> --token <token>`；
  5. 记录 QPS / P50 / P95 / P99 / 错误率，对照上表阈值。

- **写路径压测的两条硬前提**（2026-11-18 实测确认）：
  1. 必须把 `RATE_LIMIT_PER_MINUTE` 抬到远高于压测请求数，否则测出来的是
     限流器而不是系统（默认 120/分钟，500 请求会有 76% 得到 429）。
  2. 必须对**专用库或专用租户**执行：`asset_versions` 有 ADR-R11 触发器禁止
     DELETE（超级用户同样被拒），写入的压测数据**无法清理**。


### 阶段 B：多实例扩展
- 目标：验证 API 水平扩展后，连接池总量与 PostgreSQL `max_connections` 不互相
  拖垮（单实例 pool=10 上限 30，N 实例时 `max_connections` 必须 ≥ N×30 + 余量）。
- 步骤：
  1. `docker compose up --scale api=3`；
  2. 重复阶段 A 压测，对比吞吐是否线性（近似）增长；
  3. 观察 PG `max_connections` 与连接池排队，确认无连接耗尽。

### 阶段 C：故障注入
- 目标：验证降级/熔断/重试在故障下不雪崩。
- 场景清单（每项都记录「恢复时间 RTO」）：
  - [x] **Redis 宕机**（2026-11-18 本机执行）：限流 fail-open、
        `rate_limit_backend_errors_total` 递增、API 不阻塞。
        判据**不只是「不阻塞」**：修复前每请求固定阻塞 1.02s 也能叫「不阻塞」。
        真正的判据是「故障期每请求开销不随故障时长增长」——
        实测：前 3 次各 1.02s（真连、超时），第 4 次起 **12.6ms**（熔断短路），
        冷却期满第 9 次回到 1.03s（半开探测），失败后第 10 次再回 12.9ms。
        完整数据见基线文档 §3.3。
  - [ ] PG 主库短暂不可用：连接池报错后应能重连（pool_recycle=1800），不永久假死；
  - [ ] Outbox Relay 停摆：事件积压，恢复后应重放且不丢、不重（幂等）；
  - [ ] Webhook 目标超时：熔断器打开，快速失败而非无限重试；
  - [ ] 高并发下乐观锁冲突：`CONCURRENT_MODIFICATION` 可重试语义，不静默丢写。

## 4. 可观测性对照

压测全程对照 Prometheus 指标（`infra/monitoring/prometheus/outbox-rules.yml`
已含 Outbox 告警规则），确认「压测结论」与「指标曲线」一致，而非只看脚本输出：

- `http_request_duration_seconds`：延迟分位；
- `rate_limit_rejections_total`：限流命中；
- `outbox_relay_*`：Relay 吞吐与积压；
- `rate_limit_backend_errors_total`：限流后端降级计数。

## 5. 验收报告模板

每轮压测产出一份报告，至少含：

```
- 环境：实例数 / PG 版本 / 连接池参数 / 数据规模
- 压测：脚本 / 并发 / 请求数 / 时长
- 结果：QPS / P50 / P95 / P99 / 错误率 / 状态码分布
- 对照：上表阈值，逐项 PASS/FAIL
- 结论：达标 / 未达标 + 瓶颈定位（连接池 / 慢查询 / 锁竞争 / 队列背压）
```

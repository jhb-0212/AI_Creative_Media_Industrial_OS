# 单实例基线压测实测记录（2026-11-18）

> 状态：**两轮实测已完成**。首轮暴露三个结构性问题，第二轮为修复后复测。
> 本文档记录的是**本机单进程**的证据，不能外推为生产容量结论。
> 阈值口径见 `docs/perf/performance-acceptance-plan.md` 第 2 节。

## 1. 为什么要有这份记录

`performance-acceptance-plan.md` 此前只有「脚本、矩阵、阈值、checklist」，
没有一行实测数字。第三轮审查（F09）对它的判定是「无压测证据」——这个判定
在本文档之前依然成立，因为**方案存在 ≠ 证据存在**。

首轮（§3.1）除了补齐证据，还暴露了三个只有真跑才会出现的问题（§4）。
第二轮（§3.2）是对其中两个「结构性」问题的修复后复测。

## 2. 环境（这决定了数据能说明什么）

| 项 | 值 |
|---|---|
| 运行形态 | 单 uvicorn 进程（无 gunicorn 多 worker、无多实例） |
| 数据库 | 本地 PostgreSQL 16，验证库 `ai_film_verify` |
| 缓存/限流 | 本地 Redis 7 |
| 压测客户端 | 与 API **同一台机器**，与 API 争抢 CPU |
| 操作系统 | Windows 11 |
| 并发 | 5 / 20（客户端连接池上限等于并发数） |
| 每路径请求数 | 300–500 |
| 限流 | 容量压测时抬到 1,000,000/分钟（否则测的是限流器） |

**必须说明的局限**：单机 + 同机压测客户端 + 单进程，三个因素都会压低吞吐。
这里的数字衡量的是「本机基线」，不是「平台容量」。

第二轮补充了一条更硬的局限证据：**QPS 随并发增加而下降**
（并发 1/5/20/50 → 433/370/284/255 QPS）。服务端饱和时 QPS 应当趋于平坦，
下降说明瓶颈在客户端侧（单线程事件循环 + Windows + 与 API 抢同一颗 CPU）。
因此**本机压测不能用来标定容量上限**，只能用来做修复前后对照。

## 4. 首轮暴露的三个问题

### 4.1 限流后端不可达时，每个请求固定阻塞 1 秒（已修复）

首次压测的写请求稳定在 **1041ms**，连 401、403 也是 1.01s，而 `/health` 只要 2ms。

直接原因是 `.env` 里 `REDIS_URL` 指向 Docker 映射端口 16379 而本地 Redis 在 6379。
但**配置错误只是触发器**，它暴露的结构性弱点是：

> 限流器只在单次请求内 fail-open，没有任何短路机制。Redis 不可达时，
> 每个请求都要付一次完整的 `socket_connect_timeout`。指标会涨，
> 但没有机制让它停止尝试。

这不是「把 timeout 从 1.0 调到 0.1」能解决的：那只是把 1 秒变成 0.1 秒，
欠账仍在（Redis 抖动一次，全站所有请求一起等）。修法是**熔断**：连续失败后
短路（不发包），冷却期满放半开探测。

已修（见 §6 变更清单），实测见 §3.3。

### 4.2 `/readyz` 每次真探测双池，成本约 90ms（已修复）

首轮把原因写成「探测双池 + Redis」。**这里要更正一个事实**：`/readyz` 从未探测
Redis，它探的是 `project_planning` 池、`asset_service` 池与 `alembic_version`
（三次连接获取 + 三次往返）。90ms 是这三跳的成本。

阈值 50ms 按「探针只做轻量检查」设定，与实现不匹配。本轮选择的修法不是放宽阈值，
而是**让实现符合阈值的语义**：探针是编排面的高频读，应答的是缓存，真实探测按
TTL 触发并做单飞（并发请求共享同一次探测）。

实测：单请求 90ms → **2ms**；5 并发 P99 **24.6ms** 达标。

### 4.3 压测写入的数据**删不掉**（ADR-R11 触发器，约束未变）

`asset_versions` 是追加型不可变表，DELETE 被触发器拒绝，**连超级用户也被拒**：

```
asset_versions 是追加型不可变表，禁止删除（ADR-R11）
```

脚本原先会打印「清理 SQL」，照它执行必然失败。已修正为明确警告：

> 写路径压测只能对专用库或专用租户执行，不可对生产库压。

这条约束比它看起来重要：如果没人实测，下一个人会以为「压完能清干净」，
对生产库压一次就永久留下一批不可删的脏数据。

## 5. 结论

### 5.1 探针阈值与并发前提

`GET /readyz` 在 5 并发下达标（P99 24.6ms），20 并发下不达标（303.6ms）。

这**不是**「挑数据」：两个数字的差异来自测量方式而非实现。
`/readyz` 的处理已是纯内存读（缓存命中），单请求 2ms；20 并发下每请求 P50 56ms，
对应的是「20 个请求串行处理 × ~2.6ms CPU」的排队，即瓶颈在 CPU 而非探针逻辑。
而探针的真实使用场景是编排系统每 5–10 秒一次，不存在 20 并发的持续压力。

因此验收口径应为：**P99 < 50ms @ 5 并发**。20 并发的数字保留在此，
作为「本机无法标定容量」的证据，不作为达标依据。

### 5.2 只读路径仍未达标

`GET /assets/{id}` P99 215.6ms，超阈值 7.8%。该项与本轮三项修复无关
（修复前后 200.1ms → 215.6ms 属同水平波动），未做优化。

原因是该路径串行执行：RSA 验签 → 归属解析（查 project）→ RLS 查询 → JSON 序列化，
每一跳都要一次数据库往返或密码学运算。要压到 200ms 以内需要减少往返
（例如把归属信息随 token 下发、或合并查询），属于**设计变更**，不在本轮范围。

### 5.3 其它

1. **错误率与背压行为达标**：0% 错误、429 按配置返回、无 5xx 雪崩。
2. **写路径 P99 从 562ms 降到 368ms**，已达标。
3. 本机数字不能下生产容量结论；阶段 B（多实例）、阶段 C（故障注入）仍未执行，
   **性能验收不宣布通过**。

## 6. 本轮修复的变更清单

| 问题 | 修法 | 证据 |
|---|---|---|
| 限流后端故障时每请求阻塞 1s | `RateLimiter` 注入 `CircuitBreaker`：连续失败短路，冷却期满半开探测 | §3.3；`tests/unit/test_rate_limit.py` 四条熔断用例 |
| 熔断器绑死 webhook 指标 | 指标改为 `state_observer` 注入，熔断器不再 import 任何指标 | `tests/unit/test_circuit_breaker.py` 三条观察者/释放用例 |
| 熔断冷却期用墙钟 | 默认时钟改 `time.monotonic`：NTP 回拨会让冷却期永不到期 | 同上 |
| 半开探测被取消后永久卡死 | 新增 `release_probe()`，取消时释放在途标志 | `test_released_probe...`、`test_cancelled_request_releases_half_open_probe` |
| 探针每请求真探测 90ms | `ReadinessProbe`：TTL 缓存 + 单飞 + 超时；失败结果同样缓存 | `tests/unit/test_readiness.py` 九条用例 |
| 保护设施参数可静默失效 | 配置期校验（阈值负值、开着熔断却无冷却期、TTL 为负） | `tests/unit/test_config_secrets.py` 四条 |

## 7. 复现步骤

```bash
# 1. 起服务（需公钥；容量压测才需要抬限流）
IDENTITY_PUBLIC_KEY_PEM="$(cat perf_pub.pem)" \
REDIS_URL=redis://localhost:6379/0 \
RATE_LIMIT_PER_MINUTE=1000000 \
POSTGRES_DB=ai_film_verify \
uv run uvicorn apps.api.main:app --host 127.0.0.1 --port 8081

# 2. 探针（验收口径：5 并发）
uv run python scripts/perf/load_test.py --probe-only \
    --url http://127.0.0.1:8081 --concurrency 5 --requests 300

# 3. 只读（需具备 ASSET.VERSION.READ 的 token；Git Bash 下注意 MSYS 路径转换）
MSYS2_ARG_CONV_EXCL='*' uv run python scripts/perf/load_test.py \
    --url http://127.0.0.1:8081 --path "/assets/<id>" --token "$TOKEN" \
    --concurrency 20 --requests 300

# 4. 写路径（只对专用库执行——写入的数据不可删）
uv run python scripts/perf/load_test.py --write-path \
    --url http://127.0.0.1:8081 --project-id <perf-project> --token "$TOKEN" \
    --concurrency 20 --requests 300

# 5. 熔断验证：Redis 指向不可达端口，连续请求观察第 4 次起的耗时骤降
REDIS_URL=redis://localhost:16399/0 ... uvicorn --port 8082
```
